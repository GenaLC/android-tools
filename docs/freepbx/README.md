Готовые к вставке конфиги. Сервер **не трогаем** — файлы применяются вручную
после проверки.

Идентификаторы в примерах замените на свои:

| Переменная в примере | Значение | Как выбрать |
|---|---|---|

```bash
adb shell getprop gsm.sim.state      # должно быть READY, а не ABSENT
adb shell dumpsys isub | head -20    # ICCID должен быть не N/A
```

дойдёт.

### 0.2 Отдельно: телефон должен быть дефолтным набором

Входящий GSM-звонок приложение перехватывает через `InCallService`, а его
Telecom поднимает **только для дефолтного набора номера**. Пока роль не
занята, входящие звонки до шлюза не дойдут — при этом SIP остаётся
зарегистрированным и приложение выглядит полностью рабочим.

В логах это видно явно:

```
WARNING: not the default dialer (com.google.android.dialer) — incoming GSM calls will not reach the gateway
```

Проверка и выдача роли:

```bash
adb shell cmd role get-role-holders android.app.role.DIALER
adb shell cmd role add-role-holder android.app.role.DIALER com.callagent.gateway 0
```

После этого в логах должно быть `Default dialer: yes`.

### 0.3 Развёртывание идёт по UDP

TLS не поднимается. Три следствия, которые меняют конфигурацию:

1. **Порт 6064, а не 5060/5061.** В приложении: Server = `185.82.73.76`,
   Port = `6064`, Enable TLS **выкл**. Транспорт расширения в FreePBX — UDP.
2. **Пароль идёт открытым текстом — сделайте его длинным и случайным.**
   Digest-аутентификация прячет пароль в хеше, но хеш считается от nonce,
   который передаётся рядом, так что перехват регистрации даёт материал для
   подбора. Раз TLS не используется, единственная защита — стойкость самого
   пароля: 20+ случайных символов, и никаких «1001/1001».
3. **Статический IP телефону не требуется.** Шлюз представляется серверу
   именем своего аккаунта в `From` и сообщает номер вызывающего в
   `P-Asserted-Identity` (§2.3), поэтому PBX находит его **по имени**, а не
   по адресу: ни секция `identify`, ни белый IP со стороны шлюза не нужны.
   **Но** в обратную сторону (PBX звонит абоненту через шлюз) инициирует PBX:
   он шлёт INVITE на адрес из `Contact`, то есть на публичный адрес телефона.
   Операторы мобильной связи обычно не заворачивают входящие UDP-пакеты,
   инициированные извне, на устройство за CGNAT — для этого направления нужен
   статический публичный IP (свой или Wi-Fi с белым IP) либо туннель с
   обратным (WireGuard, Tailscale).

### 0.4 Важная поправка: VPN на телефоне ломает входящие звонки

Это обнаружено живой проверкой и ломает **направление PBX → GSM** (сервер
звонит абоненту через шлюз).

На телефоне активен **Surfshark VPN** (`tun1`, адрес `10.14.0.2`). Весь
интернет-трафик идёт через туннель, и сервер видит адрес **VPN-выхода**, а не
телефона:

| Что | Адрес | Когда измерено |
|---|---|---|
| Выход VPN (виден серверу) | `94.154.124.86` | с включённым Surfshark |
| Реальный WAN телефона (Starlink) | `145.224.123.93` | с выключенным Surfshark |

Два следствия:

1. **Регистрация работает** — REGISTER идёт от телефона наружу, и любой
   исходящий маршрут через VPN работает штатно.
2. **Входящий INVITE не дойдёт.** PBX отправит INVITE на `94.154.124.86` —
   это адрес VPN-сервера, общий для тысяч клиентов Surfshark. Проброс портов
   Surfshark **не поддерживает** ([источник](https://surfshark.com/blog/vpn-port-forwarding)),
   поэтому пакет от PBX не попадёт в туннель телефона. Проверено пробой с
   внешнего хоста: пакет на `94.154.124.86:5062` не появился на телефоне
   вообще.

**Что делать.** На время проверки входящих звонков VPN на телефоне надо
выключить (или исключить приложение из туннеля в настройках Surfshark —
`Split tunneling`). Тогда сервер увидит `145.224.123.93` — реальный адрес
Starlink-роутера.

Оговорка про CGNAT: адрес `145.224.123.93` принадлежит Starlink, и входящие
UDP-пакеты на произвольный порт (5062) до роутера обычно **не доходят** —
для этого нужен проброс порта на роутере Starlink (`UDP 5062 → 192.168.1.42`)
либо туннель с обратным входом (WireGuard, Tailscale) между телефоном и
сервером. Проверяется так: с внешнего хоста отправить UDP на
`145.224.123.93:5062` и посмотреть, появился ли пакет на телефоне
(`tcpdump -i any udp port 5062`).

> Направление **GSM → PBX** (абонент звонит на SIM, шлюз звонит в PBX) от VPN
> не зависит: там инициирует телефон, и REGISTER/INVITE идут наружу
> штатно.

### 0.5 Эндпоинту `1001` нужен `rewrite_contact` (это важно)

Шлюз объявляет себя в `Contact` как `sip:1001@<публичный адрес>:<порт>`.
Порт в этом заголовке — тот, что приложение знает о себе локально (5062), а
не тот, что выдал NAT. Сервер, получив REGISTER, запоминает адрес, **откуда
пришёл пакет**, — и вот на него он и отправит INVITE.

Заставить сервер пользоваться реальным адресом можно двумя настройками
эндпоинта `1001` (в `pjsip.endpoint.conf`):

```ini
rewrite_contact=yes
rtp_symmetric=yes
```

- `rewrite_contact=yes` — сервер переписывает `Contact` в контакте на адрес
  источника REGISTER. Это то, что нужно за NAT.
- `rtp_symmetric=yes` — RTP-трафик тоже идёт на адрес, откуда пришёл.

Проверка:

```bash
asterisk -rx "pjsip show endpoint 1001" | grep -E "rewrite_contact|rtp_symmetric"
```

В `pjsip show contacts` колонка `Contact` должна совпадать с тем, что
пришло в REGISTER — тогда INVITE уйдёт туда, куда надо.

> Если эти опции выключены, входящий INVITE уйдёт на `Contact` из
> заголовка — то есть на локальный адрес/порт, который снаружи не
> существует, и звонок просто не дойдёт. Ошибка при этом выглядит как
> «сервер звонит, а на шлюзе тишина», без внятного сообщения.

### 0.6 Как это делается в GUI FreePBX 16.0.50

Точный список полей — в отдельном файле: **[`SETUP.md`](SETUP.md)** (что
вписать и куда, плюс команды проверки). Здесь — логика и решения.

Меню именно этой версии (Asterisk 18.26.4). Порядок — от расширения к
маршрутам.

**Шаг 1. Расширение шлюза.**
`Applications → Extensions → Add Extension → Device` → Device Type: **SIP
Phone**.

| Поле | Значение |
|---|---|
| Extension Number | `1001` |
| Display Name | GSM Gateway |
| Secret | пароль шлюза (тот же, что в приложении) |
| Advanced → Context | `from-gsm-gateway` |
| Advanced → Transport | **UDP** (транспорт `0.0.0.0-udp`, порт 6064) |
| Advanced → Outbound Proxy | пусто |
| Advanced → Codecs | `g722`, `alaw`, `ulaw` (см. §6) |
| Advanced → Direct Media | No |
| Advanced → RTP Symmetric / Rewrite Contact | Yes |
| Advanced → **Trust RPID** | **Yes** |
| Advanced → **Send RPID** | **Send P-Asserted-Identity header** |

> **Trust RPID** — подпись в GUI старая, это опция `trust_id_inbound`
> из res_pjsip — «принимать идентификацию, присланную устройством». Ровно
> она нужна, чтобы номер GSM-вызывающего из `P-Asserted-Identity` стал
> CallerID'ом, а не именем учётной записи шлюза (1001).
>
> **Send RPID** — обратная сторона: что PBX кладёт в заголовок номера
> вызывающего, когда звонит **на** этот эндпоинт. Варианты в выпадающем
> списке: **No** (ничего не шлёт), **Send Remote-Party-ID header**
> (`send_rpid=yes`), **Send P-Asserted-Identity header** (`send_pai=yes`).
> Для 1001 выбираем PAI: когда PBX звонит шлюзу (направление PBX → GSM), он
> сообщает CallerID исходящего маршрута, а это номер SIM, и шлюз выбирает
> SIM именно по нему. Шлюз читает номер вызывающего в порядке
> `P-Asserted-Identity` → `Remote-Party-ID` → `From`, так что PAI попадает
> первым.

**Шаг 2. Dialplan.**
`Administration → Config Edit` → слева **Asterisk Custom Configuration
Files** → `extensions_custom.conf` → вставить блок из §4 → Save →
**Apply Config**. FreePBX этот файл не перезаписывает, в отличие от
`extensions.conf`.

**Шаг 3. Передача PAI дальше, к 40181.**
То же самое делается прямо в GUI, без Config Edit. Откройте расширение
**40181** (`Applications → Extensions`) → **Advanced** → поле **Send RPID** →
**Send P-Asserted-Identity header** → Save & Apply.

Иначе PBX отдаст софтфону CallerID самого эндпоинта («40181») вместо номера
GSM-вызывающего.

Если какой-то конкретный софтфон номер всё равно не показывает, поставьте
вместо PAI вариант **Send Remote-Party-ID header** (`send_rpid=yes`) — часть
клиентов читает только RPID. Шлюз этот заголовок тоже понимает, у него в
приоритете он второй.

**Шаг 3.1. `identify` для входящих GSM — не требуется.**
Шлюз представляется именем аккаунта в `From` (§2.3), поэтому PBX находит его
по имени, а не по адресу. Если секцию `identify` всё же создадите, `match`
должен быть точным адресом, иначе она будет мешать.

**Шаг 4. Исходящий маршрут.**
`Connectivity → Outbound Routes → Add Outbound Route`:

| Поле | Значение |
|---|---|
| Name | GSM через шлюз |
| Route Settings → Route CID | номер SIM шлюза в E.164 |
| Route Settings → Override Extension | Yes |
| Dial Patterns → Match Pattern | `+X.` (или `00X.`, если агенты набирают международный через 00) |
| Dial Patterns → CallerID | **пусто** (это фильтр, а не «куда передать номер») |
| Trunks | **SIP Phone → 1001** |

**Шаг 5. Проверка.**
`Administration → Config Edit` → `pjsip.endpoint.conf` — там видно, что
FreePBX собрал эндпоинт; `pjsip.registrations` — на сервере.

## 1. Что шлюз читает из INVITE

Из нестандартных заголовков шлюз читает **ровно один**:

| Заголовок | Кто его шлёт | Что значит |
|---|---|---|
| `X-GSM-Forward: <номер>` | PBX, в INVITE, который уходит шлюзу | Номер, который шлюз должен набрать по SIM. Если заголовка нет, шлюз берёт номер из user-части Request-URI, а если и там не номер — из user-части `To` |

> **Почему нужны оба URI.** res_pjsip собирает Request-URI из AOR
> эндпоинта, а «дозвонную часть» кладёт в заголовок `To`:
> `Dial(PJSIP/1001/+4915112345678)` приходит как Request-URI `sip:1001@pbx`
> и `To: sip:+4915112345678@pbx`. Поэтому шлюз смотрит обе заголовка — в
> зависимости от диал-строки сервера номер оказывается то в одном, то в
> другом.

Всё остальное шлюз берёт из **стандартных** заголовков SIP:

| Что | Где шлюз это ищет | Комментарий |
|---|---|---|
| Номер вызывающего | `P-Asserted-Identity` → `Remote-Party-ID` → `From` | порядок именно такой; если PBX не добавляет PAI, номер остаётся в `From` |
| Номер назначения | Request-URI | user-часть, если это «голый» номер |

Заголовков `X-GSM-From` и `X-GSM-To` шлюз **не понимает и не читает** —
в предыдущей версии этого документа они были описаны неверно. Если сервер
шлёт только их, шлюз не найдёт адресата и ответит `488 Not Acceptable Here`.

В обратную сторону (GSM → PBX) шлюз шлёт один нестандартный заголовок:

| Заголовок | Что значит |
|---|---|
| `P-Asserted-Identity: <номер GSM-вызывающего>` | Кто на линии. Шлюз при этом представляется **своим именем аккаунта** в `From` — см. §2.3 |

## 2. Два направления

### 2.1 PBX → GSM (сервер звонит абоненту через сотовную ногу)

PBX отправляет шлюзу INVITE на зарегистрированное расширение `1001` и кладёт
в него `X-GSM-Forward: <номер абонента>`. Шлюз дозванивается по SIM, снимает
трубку, отвечает `200 OK` с SDP и мостит аудио между RTP-сессией и сотовной
ногой.

Заголовок должен попасть **в тот INVITE, который уходит шлюзу**. Обычный
`Set(PJSIP_HEADER(add,...))` в контексте dialplan добавляет заголовок
**вызывающему** каналу и в исходящий INVITE, созданный `Dial()`, не
наследуется — то есть заголовок до шлюза не доезжает. Работают два варианта:

**Вариант A — наследуемый заголовок** (Asterisk **20.19+ / 22.9+ / 23.3+**,
`res_pjsip_header_funcs`). **На вашем сервере (Asterisk 18.26.4) этого варианта
нет** — см. Вариант B ниже:

```ini
[gsm-outbound]
; Агент звонит на номер абонента в международном формате (+4915...).
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,Set(PJSIP_INHERITABLE_HEADER(add,X-GSM-Forward)=${GW_DEST})
 same => n,Dial(PJSIP/1001,60)
 same => n,Hangup()
```

`PJSIP_INHERITABLE_HEADER` — это **функция** dialplan, а не приложение, и
вызывается она через `Set(...)`. Написать её в dialplan голой строкой
(`same => n,PJSIP_INHERITABLE_HEADER(add,X-GSM-Forward)=...`) нельзя: там
ожидается приложение, Asterisk напишет «No application ... for extension» и
пропустит действие — заголовок просто не добавится, а шлюз ответит `488`.

Функция появилась в Asterisk 20.19.0, 22.9.0 и 23.3.0. **Версии 16 и 18 её
не имеют** — а на них стоят FreePBX 15 и 16. Если `core show function
PJSIP_INHERITABLE_HEADER` ничего не выводит, используйте Вариант B: он
работает везде, где есть `b()` в `Dial()`.

**Вариант B — pre-dial-обработчик** (любая версия, где есть `b()` в `Dial()`):

```ini
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,Dial(PJSIP/1001,60,b(add-gsm-forward^s^1(${EXTEN})))
 same => n,Hangup()

; В pre-dial-обработчике PJSIP_HEADER(add,...) работает с каналом
; ВЫЗЫВАЕМОГО — поэтому заголовок уезжает в INVITE, который уходит шлюзу.
; Номер передан аргументом (после третьего ^), а не переменной: аргумент
; доезжает наверняка, а наследование переменных вызывающего канала
; зависит от того, как Dial() создал вызываемый канал.
[add-gsm-forward]
exten => s,1,Set(PJSIP_HEADER(add,X-GSM-Forward)=${1})
 same => n,Return()
```

Формат опции `b()`: `b(контекст^экстеншн^приоритет(аргумент1^аргумент2…))`.
Аргументы пишутся **в скобках** и приходят в обработчик как `${1}`, `${2}` и так
далее. Без скобок Asterisk не поймёт, где кончился приоритет, — и номер не
доедет. Так пишет и сам Asterisk в подсказке к `Dial()`:
`b([[context^]exten^]priority[(arg1[^...][^argN])])`.

**Ваш сервер — Asterisk 18.26.4** (проверено на freepbx-c): функции
`PJSIP_INHERITABLE_HEADER` в ветке 18 нет, она появилась в 20.19.0, 22.9.0 и
23.3.0. Поэтому на вашем сервере применяется **Вариант B**. Убедиться можно
одной командой:

```bash
asterisk -rx "core show function PJSIP_INHERITABLE_HEADER"
```

Если она ответит «No such function» — Вариант A невозможен, это не ошибка
конфигурации, а версия Asterisk.

### 2.2 GSM → PBX (абонент звонит на SIM, шлюз звонит в PBX)

При входящем GSM-вызове шлюз сам отправляет INVITE на **собственный номер
SIM** в международном формате (`+4915112345678`), который настроен в
приложении (Settings → «Own number») или читается с SIM. Номер вызывающего
идёт в `From` (и в `P-Asserted-Identity`, если PBX его добавляет).

Запрос приходит на зарегистрированный эндпоинт `1001`, поэтому его контекст
должен быть `from-gsm-gateway`.

```ini
[from-gsm-gateway]
; To в INVITE = <sip:+4915112345678@pbx> — это собственный DID шлюза.
exten => _+X.,1,NoOp(GSM gateway: inbound from ${CALLERID(num)})
 same => n,Set(GW_FROM=${CALLERID(num)})
 same => n,Set(GW_FROM=${GW_FROM:0})        ; если транк ждёт номер без "+"
 same => n,Dial(PJSIP/trunk-name/${GW_FROM},60)
 same => n,Hangup()
```

`${CALLERID(num)}` на PJSIP-канале — это user-часть `From`, то есть номер
GSM-вызывающего. Если PBX добавляет `P-Asserted-Identity`, его можно читать и
явно: `${PJSIP_HEADER(read,P-Asserted-Identity)}` — шлюз тоже смотрит в него
первым.

### 2.3 Как шлюз представляется серверу (GSM → PBX)

Когда звонит абонент на SIM, шлюз сам ставит INVITE на PBX. Он делает это
**от своего имени** и отдельно сообщает, кто на линии:

```
From: <sip:1001@pbx>;tag=...
P-Asserted-Identity: <sip:+4915112345678@pbx>
```

Именно так, а не номером вызывающего в `From`. Причина — в том, как сервер
ищет эндпоинт для входящего запроса:

1. по имени пользователя в `From` — это имя должно быть расширением;
2. по `Contact` зарегистрированного AOR — работает для REGISTER;
3. по адресу источника — это и есть `identify` (§5).

Номер GSM-вызывающего расширением не является, поэтому в `From` он не
подходит: запрос не нашёл бы эндпоинт ни по первому, ни по второму
признаку, и остался бы только третий — `identify` с литеральным адресом. А
`identify` требует, чтобы адрес телефона был статическим и известным PBX:
телефон за CGNAT мобильного оператора такому условию не удовлетворяет.

С именем аккаунта в `From` первый признак срабатывает всегда: запрос
находит эндпоинт `1001` **с любого адреса**, и ни `identify`, ни статический
IP не нужны. Номер вызывающего при этом не теряется — он в
`P-Asserted-Identity`, и PBX берёт его оттуда, если у эндпоинта включён
`trust_id_inbound=yes` (см. §3).

Обратная сторона: если `trust_id_inbound` выключен, PBX покажет вместо
номера вызывающего имя учётной записи шлюза. Поэтому `trust_id_inbound=yes`
для этого эндпоинта — обязателен, а не «для красоты».

## 3. Требования к pjsip.conf

Если вы работаете через веб-панель FreePBX, создайте расширение
**Administration → Extensions → Add Extension → Device** с этими значениями:

| Поле | Значение |
|---|---|
| Extension Number | `1001` |
| Device Type | Device |
| Secret / Password | пароль шлюза |
| Context | `from-gsm-gateway` (см. §4) |
| Advanced → Codecs | `g722` и `alaw`/`ulaw` (см. §6) |
| Advanced → Transports | **UDP** (TLS — необязательно, см. §5) |
| Advanced → Outbound Proxy | пусто (шлюз регистрируется к нам, не наоборот) |
| Advanced → RTP → Direct Media | No |
| Advanced → Trust RPID | Yes (`trust_id_inbound`) |
| Advanced → Send RPID | Send P-Asserted-Identity header (`send_pai`) |

Готовые файлы конфигурации:

```ini
; /etc/asterisk/pjsip.conf

; Транспорты. Приложение умеет только UDP и TLS — «голого» SIP поверх TCP
; в нём нет, и эндпоинт с transport=tcp не зарегистрируется.
;
; ВНИМАНИЕ: на вашем сервере транспорт уже есть и называется 0.0.0.0-udp,
; слушает 0.0.0.0:6064. Этот файл FreePBX генерирует сам, руками он не
; правится. Секция ниже — для случая, когда транспорт создают заново.
[transport-udp]
type=transport
protocol=udp
bind=0.0.0.0:6064

; TLS-транспорт в текущей схеме не используется. Если решите включить его
; позже, то: сертификат у транспорта называется cert_file / priv_key_file
; (tls_cert_file / tls_key_file — это из chan_sip, транспорт их не понимает),
; и нужна строка method=tlsv1_2 — Android 15 не согласует TLS 1.0/1.1.
[transport-tls]
type=transport
protocol=tls
bind=0.0.0.0:5061
cert_file=/etc/asterisk/keys/asterisk.crt
priv_key_file=/etc/asterisk/keys/asterisk.key
method=tlsv1_2
verify_client=no
verify_server=yes

[1001]
type=endpoint
; Контекст входящих вызовов от шлюза (и звонков на 1001 от агентов).
context=from-gsm-gateway
transport=transport-udp
; Медиа не шоркаутим: Asterisk — B2BUA, RTP между агентом и шлюзом идёт
; через Asterisk, шлюз держит вторую ногу (сотовую) сам.
; Прямой медиа запрещён ещё и потому, что шлюз не пересогласовывает медиа
; по re-INVITE и продолжает слать RTP на запомненный адрес.
direct_media=no
; Телефон стоит за NAT.  Без rtp_symmetric Asterisk отправил бы RTP на
; локальный адрес телефона из SDP — соединение установилось бы, но в трубке
; было бы молчание.
rtp_symmetric=yes
force_rport=yes
rewrite_contact=yes
; Кодеки. Шлюз по умолчанию предлагает 9 8 0 101:
;   9 = G722, 8 = PCMA (A-law), 0 = PCMU (µ-law), 101 = telephone-event.
; Эндпоинт обязан разрешать хотя бы один аудиокодек из предложения шлюза,
; иначе предложение неприемлемо и звонок не состоится.
allow=!all,g722,alaw,ulaw
; Учётные данные, по которым PBX проверяет REGISTER и INVITE шлюза.
; ВАЖНО: без этой опции эндпоинт принимает соединения БЕЗ проверки, а
; несуществующей опции `authenticate` (её нет ни у endpoint, ни у aor ни в
; Asterisk 20, ни в 23) достаточно, чтобы секция не загрузилась вовсе.
; Имя секции auth начинается с буквы: имя, начинающееся с цифры, sorcery
; не находит — известная ошибка FreePBX, лечится именно так.
auth=auth1001
aors=1001
callerid=GSM Gateway
; Шлюз представляется именем аккаунта в From, а номер GSM-вызывающего
; присылает в P-Asserted-Identity (§2.3).  Без доверия к идентификации PBX
; покажет вместо номера вызывающего CallerID самого эндпоинта ("1001").
; В GUI FreePBX 16 это чекбокс Advanced → "Trust RPID".
trust_id_inbound=yes
; Передать P-Asserted-Identity дальше, тем, кому PBX звонит.  На эндпоинте
; шлюза это нужно в обратную сторону: когда PBX звонит на 1001 (PBX → GSM),
; он сообщает CallerID исходящего маршрута, а это номер SIM, и шлюз выбирает
; SIM именно по нему.  На эндпоинте получателя (40181) — тоже нужно, иначе
; софтфон покажет "40181" вместо номера GSM-вызывающего.  В GUI FreePBX 16 это
; поле Advanced → "Send RPID" со значением "Send P-Asserted-Identity header".
send_pai=yes
; Не отвечать 180 раньше времени: шлюз сам сообщает 180, когда пошла
; сотовная нога.
; SRTP по умолчанию не включаем: G.722 достаточно, а SRTP добавляет
; согласование ключей, которое придётся проверять отдельно.
; Включать, если транк требует:
;media_encryption=sdes
;media_encryption=dtls
; Свои SIP-заголовки не отбрасываем.
; (allow_transfer — это про SIP REFER, т.е. перевод звонка средствами
; сервера.  К заголовкам X-GSM-Forward он отношения не имеет: тот
; добавляется dialplan'ом, см. §2.1.)
allow_transfer=yes

[1001]
type=aor
max_contacts=1
remove_existing=yes
qualify_frequency=60

[auth1001]
type=auth
auth_type=userpass
username=1001
password=CHANGE_ME_STRONG_PASSWORD
```

Идентификаторы `1001` в секциях `endpoint`/`aor`/`auth` — одинаковые имена
секций в PJSIP допустимы (это разные типы), но во FreePBX UI они
создаются автоматически.

## 4. `extensions.conf` — маршрутизация

В FreePBX `extensions.conf` генерируется и перезаписывается при каждом
изменении через GUI. Свой dialplan туда класть нельзя — он исчезнет. Правильное
место — **`extensions_custom.conf`** (Administration → Advanced → Custom
Context, или Config Edit → `extensions_custom.conf`).

```ini
; /etc/asterisk/extensions_custom.conf

; ── Исходящий: агент звонит абоненту через сотовную ногу шлюза ──
; Контексты и приложения — см. §2.1.
; Вариант B: pre-dial-обработчик (на Asterisk 18 функции
; PJSIP_INHERITABLE_HEADER нет).
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,Dial(PJSIP/1001,60,b(add-gsm-forward^s^1(${EXTEN})))
 same => n,Hangup()

[add-gsm-forward]
exten => s,1,Set(PJSIP_HEADER(add,X-GSM-Forward)=${1})
 same => n,Return()

; ── Входящий: абонент звонит на SIM, шлюз звонит в PBX ──
; См. §2.2.
[from-gsm-gateway]
exten => _+X.,1,NoOp(GSM gateway: inbound from ${CALLERID(num)})
 same => n,Set(GW_FROM=${CALLERID(num)})
 same => n,Set(GW_FROM=${GW_FROM:0})
 same => n,Dial(PJSIP/trunk-name/${GW_FROM},60)
 same => n,Hangup()

; Прямые звонки на 1001 от агента (номер абонента передаётся в аргументе):
;   1001 + 79001234567 → агент звонит на 100179001234567
exten => _1001X.,1,NoOp(GSM gateway: agent dialled the gateway with a number)
 same => n,Set(GW_DEST=${EXTEN:4})
 same => n,Goto(gsm-outbound,${GW_DEST},1)
```

### 4.1 Маршрутизация на конкретного SIP-клиента (пример — 40181)

Пусть `40181` — обычный SIP-клиент (софтфон или IP-телефон), зарегистрированный
в FreePBX, и он должен звонить в PSTN через сотовную ногу шлюза.

**40181 → PSTN через шлюз.** Номер кладём в Request-URI — тогда заголовок не
нужен вовсе, и конфиг работает на любой версии Asterisk:

```ini
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Dial(PJSIP/1001/${EXTEN},60)
 same => n,Hangup()
```

`Dial(PJSIP/1001/…)` — Asterisk находит эндпоинт `1001`, берёт его
зарегистрированный contact и отправляет INVITE, у которого номер стоит в
user-части Request-URI. Шлюз читает оттуда номер, если не пришёл
`X-GSM-Forward`.

Заголовок нужен только когда номер, который надо набрать, отличается от
адресуемого расширения: агент звонит на `1001`, а звонить надо на
`+79001234567`. Тогда — §2.1, вариант A или B.

**PSTN → SIM → 40181.** Звонок приходит на SIM, шлюз шлёт INVITE на собственный
номер SIM (`To: +4915112345678`), и его ловит `identify` (см. §5) — запрос
попадает в контекст `from-gsm-gateway`, который и должен дозвониться до 40181:

```ini
[from-gsm-gateway]
exten => _+X.,1,NoOp(GSM gateway: inbound from ${CALLERID(num)})
 same => n,Dial(PJSIP/40181,60)
 same => n,Hangup()
```

**CallerID исходящего маршрута — это номер SIM.** Шлюз берёт номер вызывающего
из `P-Asserted-Identity` → `Remote-Party-ID` → `From`, а из него выбирает SIM
на двухсимочном телефоне и ставит его CallerID в сторону PSTN. Если в маршруте
оставить CallerID `40181`, то:

- на двухсимочном шлюзе не найдётся SIM под такой номер → `503 No Matching SIM`;
- в PSTN абонент увидит номер `40181` вместо номера SIM.

Поэтому в Outbound Route (Route Settings → **Route CID**, Override Extension =
Yes) / в `Set(CALLERID(num))=…)` нужно поставить номер SIM
того же шлюза, на котором работает расширение `1001`.

Не путайте это с полем **Dial Patterns → CallerID**: оно не «передаёт номер
дальше», а **фильтрует**, какие вызывающие могут уйти по этому маршруту (для
внутренних вызовов сравнивается номер расширения, а не его Outbound CID).
Если вписать туда номер SIM, маршрут не сработает никогда: звонит `40181`, а
фильтр ждёт `+49…`.

Чтобы этот номер доехал до шлюза в заголовке, у эндпоинта `1001` должно стоять
**Advanced → Send RPID = Send P-Asserted-Identity header** (`send_pai=yes`).
Без этого PBX номер вызывающего не положит ни в PAI, ни в RPID, и шлюз возьмёт
его из `From` — а там в новой схеме может оказаться имя аккаунта, и выбора SIM
не будет.

**Петли.** Шлюз исключает из набора номера свой собственный номер и имя
аккаунта (`1001`): позвонить самому себе через Request-URI он не станет, но и
не отправит INVITE туда, откуда он пришёл. Поэтому маршрут «1001 → 1001»
работает как «позвонить абоненту по номеру», а не как петля.

**Где в FreePBX это настраивается.**

| Что | Где |
|---|---|
| Регистрация шлюза | Administration → Extensions → Add Extension → SIP Phone (или pjsip.conf вручную, §3) |
| `gsm-outbound` / `from-gsm-gateway` | Config Edit → `extensions_custom.conf` |
| Исходящие 40181 → PSTN | Administration → Routes → Outbound Routes → Destination: SIP Phone/Extension или транк на `1001`; CallerID = номер SIM |
| Входящие SIM → 40181 | `from-gsm-gateway` в `extensions_custom.conf` **или** Inbound Route на DID = номер SIM → Destination: SIP Phone 40181 (тогда `context` эндпоинта надо поставить `from-trunk`, чтобы сработала штатная маршрутизация FreePBX) |
| Проверка | `pjsip show endpoint 1001`, `pjsip show contacts`, `pjsip show registrations` |

### Про `Dial()` и таймаут

Для GSM-замыкания нужно **не меньше 60 секунд**: время установки сотовной
ноги (дозвон, ответ абонента) существенно больше длительности SIP-транзакции.
20 секунд — недостаточно, разрыв будет выглядеть как таймаут.

## 5. `identify` и адрес шлюза

**Секция `identify` не нужна.** Шлюз представляется серверу именем своего
аккаунта в `From` и сообщает номер вызывающего в `P-Asserted-Identity`
(§2.3), поэтому входящий INVITE шлюза находится по имени в `From` — с любого
адреса. Ниже — для полноты: как это выглядит, если секция всё-таки нужна
(например, для `MESSAGE`/SMS, где регистрации нет вовсе).

Сопоставление запроса с эндпоинтом в `res_pjsip` идёт по трём признакам:
адрес источника (`identify`), имя пользователя в `From` и — для REGISTER —
имя AOR в `To`:

| Что приходит от шлюза | Чем сопоставляется | Нужен ли `identify` |
|---|---|---|
| REGISTER (`To: 1001`) | AOR по имени в `To` | нет |
| INVITE от PBX к шлюзу (`To: 1001` или `To: +49…`) | зарегистрированный contact | нет |
| INVITE от шлюза при входящем GSM (`From: 1001`, `To: +49…`) | **имя в `From`** | **нет** |

```ini
; /etc/asterisk/pjsip.conf — только если понадобится
[1001]
type=identify
endpoint=1001
match=192.168.1.10
```

Оговорки, если секцию всё же пришлось добавить:

- адрес должен быть **статическим**: за динамическим адресом (DHCP) или за
  NAT, где внешний адрес меняется, `identify` перестаёт совпадать и запросы
  снова не находятся. Телефон, выходящий в интернет через CGNAT мобильного
  оператора, такому требованию не удовлетворяет;
- `match` — это адрес, с которого PBX **видит** шлюз: тот, что стоит в
  `Contact` зарегистрированного шлюза (`pjsip show contacts`), а не адрес
  интерфейса телефона;
- `message_context` в связке с `identify` нужен только для исходящего
  `MESSAGE` (SMS) — это вне рамок задачи «звонки».

## 6. Кодеки

**Поведение изменено:** по умолчанию шлюз предлагает
`9 8 0 101` — G.722, PCMA (A-law), PCMU (µ-law) и telephone-event. Раньше
по умолчанию предлагался только G.722 (`9 101`), и эндпоинт, разрешающий
только `alaw`/`ulaw`, отвечал на это `488 Not Acceptable` — звонок не
начинался вовсе.

Что это значит для конфигурации:

| `allow` на эндпоинте | Что выберет Asterisk | Результат |
|---|---|---|
| `!all,g722,alaw,ulaw` | G.722 (его порядок предпочтений первый) | широкополосный RTP (16 кГц); имеет смысл только при AMR-WB на сотовной стороне |
| `!all,alaw,ulaw` | PCMA (A-law) | узкополосный RTP (8 кГц) — совпадает с сотовной ногой (AMR-NB) и гарантирован транком |
| `!all,ulaw` | PCMU (µ-law) | узкополосный RTP (8 кГц), µ-law |

Кодек выбирают **разные стороны в разных направлениях**.

**GSM → PBX** кодек выбирает **Asterisk**, по своему порядку `allow`: шлюз
предлагает `9 8 0 101`, и сервер берёт первый из своих. Ответ `200 OK`
перечисляет только согласованный payload (например `m=audio 5000 RTP/AVP 8
101`), поэтому предложение и ответ всегда согласованы и оба конца
используют один кодек.

**PBX → GSM** кодек выбирает **шлюз**: там Asterisk — вызывающий, он
присылает INVITE с оффером, а шлюз отвечает, и отвечает тем кодеком,
который предпочитает сам (G.722 > PCMA > PCMU) из тех, что есть в оффере.
Поэтому при `allow=!all,ulaw,alaw` в этом направлении Asterisk не сможет
навязать µ-law: шлюз ответит PCMA. Ответ и реально отправляемый RTP всегда
совпадают — расхождения между ними быть не может.

Если нужен строго G.722, выберите в приложении Settings → Codec режим
«G.722 only»: тогда предложение шлюза будет `9 101`, и эндпоинт должен
разрешать `g722`. Обратная сторона «по умолчанию всё» — если сервер
предпочитает G.711, разговор останется узкополосным; для сотовной ноги это
не цена: она и так 8 кГц.

## 7. TLS — необязательно

**В текущей схеме TLS не используется:** связь идёт по UDP на порт 6064,
в приложении Enable TLS выключен, CA импортировать не нужно. Раздел оставлен
на случай, если решите включить шифрование позже.

Приложение умеет говорить и по SIP over TLS, и проверяет при этом цепочку
сертификатов **и** имя хоста — опции «доверять всем» у него нет (иначе пароль
от регистрации ушёл бы кому попало). Чтобы это заработало, нужно три вещи:

- сертификат должен выдавать CA, которому доверяет телефон. Публичный CA
  (Let's Encrypt) — если есть имя, доступное телефону; либо собственный CA,
  который **импортируется в приложение** (Settings → Certificate authority
  (private PBX) → IMPORT CA). Импорт добавляет якорь к системному хранилищу,
  а не заменяет его;
- имя в поле Server должно совпадать с SAN сертификата. Подключение по IP
  тоже работает, но тогда в сертификате должен быть SAN типа iPAddress:
  `tools/gen-pbx-cert.sh --host 10.0.0.5` добавляет его сам;
- версия TLS — **1.2 или 1.3**. Android 15 запрещает TLS 1.0/1.1 для
  приложений с `targetSdk 35`, поэтому шлюз их не предлагает, а транспорт PBX
  должен быть `method=tlsv1_2` (Settings → Asterisk SIP Settings →
  `chan_pjsip` → SSL Method).

Полная процедура — в [`../TLS.md`](../TLS.md): создание CA и сертификата,
установка на PBX, импорт CA на телефоне и расшифровка ошибок в логе.

Проверка на стороне PBX:

```bash
asterisk -rx "pjsip show tls"
asterisk -rx "pjsip show transports"
```

## 8. Проверка на сервере

```bash
# Регистрация шлюза
asterisk -rx "pjsip show registrations"
asterisk -rx "pjsip show endpoint 1001"

# Входящий INVITE от шлюза: должен попасть в контекст from-gsm-gateway
asterisk -rx "dialplan show from-gsm-gateway"

# Живой вызов: смотрим заголовок на входящем INVITE
grep -E "X-GSM-Forward" /var/log/asterisk/full

# Исходящий: заголовок на канале к шлюзу и согласованный кодек
asterisk -rx "pjsip show channelstats"
```

Типичные ошибки:

| Симптом | Причина |
|---|---|
| `No matching endpoint found` | Регистрация не прошла или contact не совпадает; проверьте `pjsip show registrations`. Если адрес шлюза меняется — см. §5 про `identify` |
| Шлюз отвечает `488` | В INVITE нет `X-GSM-Forward`, а user-часть Request-URI не похожа на номер — шлюзу нечего dial'ить |
| Заголовок `X-GSM-Forward` не видно в `full` | `PJSIP_HEADER(add,...)` в обычном контексте добавляет его вызывающему каналу и не наследуется в INVITE от `Dial()` — нужен `PJSIP_INHERITABLE_HEADER` либо pre-dial-обработчик (§2.1) |
| Звонок идёт, но через ~20 с обрывается | Слишком короткий `Dial()` — поставьте 60 |
| Звонок идёт, звука нет, в `channelstats` другой кодек | Эндпоинт разрешает не тот кодек, который согласован; сверьте `allow` с §6 |
| Входящий от SIM не маршрутизируется | Контекст эндпоинта не `from-gsm-gateway` либо `Dial()` уходит не в тот транк |
| `no usable TLS version ...` в логе телефона | Транспорт PBX ограничен TLS 1.0/1.1; нужен `method=tlsv1_2` — см. §7 и `../TLS.md` |

## 9. Замечания по RTCP

Шлюз не реализует RTCP и не объявляет `a=rtcp` в своём SDP. RTCP-трафик
Asterisk уходит на порт RTP + 1 и остаётся без ответа. На передачу голоса
это не влияет: RTCP не несёт звука, а таймаут RTP на стороне Asterisk
задаётся отдельно (`rtp_timeout` / `rtp_timers=yes`).

## 10. Что нужно от оператора сотовой связи

- Номер SIM должен принимать входящие вызовы (для направления GSM → SIP).
- Номер должен быть в E.164; он же используется как DID шлюза в направлении
  GSM → PBX (см. §2.2).
- Если SIM заведена с **VoWiFi (WFC)** — его нужно отключить: в режиме WFC
  сотовной ноги нет, модемного аудио-канала не существует, мост невозможен.
- При **VoLTE/IMS** голос идёт пакетным вызовом; работает ли аудио-мост на
  IMS-вызове, проверяется на живом вызове (см. `docs/DEPLOYMENT.md`).
