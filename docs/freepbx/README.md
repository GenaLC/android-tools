# FreePBX: PJSIP-эндпоинт и dialplan для GSM-SIP шлюза

Готовые к вставке конфиги. Сервер **не трогаем** — файлы применяются вручную
после проверки.

Идентификаторы в примерах замените на свои:

| Переменная в примере | Значение | Как выбрать |
|---|---|---|
| `1001` | Номер расширения, под которым шлюз регистрируется в PBX | Свободный номер в вашем плане нумерации |
| `+4915112345678` | Номер SIM-шлюза в строгом E.164 | Номер, на который шлюз звонит сам, когда абонент звонит на SIM (DID шлюза) |
| `trunk-name` | Имя вашего PSTN-транка в PJSIP | Как он назван в FreePBX |
| `192.168.1.10` | Адрес шлюза в сети PBX | Статический адрес; см. §5 про `identify` |

## 1. Что шлюз читает из INVITE

Из нестандартных заголовков шлюз читает **ровно один**:

| Заголовок | Кто его шлёт | Что значит |
|---|---|---|
| `X-GSM-Forward: <номер>` | PBX, в INVITE, который уходит шлюзу | Номер, который шлюз должен набрать по SIM. Если заголовка нет, шлюз берёт номер из user-части Request-URI (если это не имя аккаунта и не собственный номер SIM) |

Всё остальное шлюз берёт из **стандартных** заголовков SIP:

| Что | Где шлюз это ищет | Комментарий |
|---|---|---|
| Номер вызывающего | `P-Asserted-Identity` → `Remote-Party-ID` → `From` | порядок именно такой; если PBX не добавляет PAI, номер остаётся в `From` |
| Номер назначения | Request-URI | user-часть, если это «голый» номер |

Заголовков `X-GSM-From` и `X-GSM-To` шлюз **не понимает и не читает** —
в предыдущей версии этого документа они были описаны неверно. Если сервер
шлёт только их, шлюз не найдёт адресата и ответит `488 Not Acceptable Here`.

## 2. Два направления

### 2.1 PBX → GSM (сервер звонит абоненту через сотовную ногу)

PBX отправляет шлюзу INVITE на зарегистрированное расширение `1001` и кладёт
в него `X-GSM-Forward: <номер абонента>`. Шлюз дозванивается по SIM, снимает
трубку, отвечает `200 OK` с SDP и мостит аудио между RTP-сессией и сотовной
ногой.

Заголовок должен попасть **в тот INVITE, который уходит шлюзу**. Обычный
`Set(PJSIP_HEADER(add,...))` в контексте dialplan добавляет заголовок
**вызывающему** каналу и в исходящий INVITE, созданный `Dial()`, не
наследуется — то есть заголовок до шлюза не доезжает. Работают два варианта:

**Вариант A — наследуемый заголовок** (Asterisk 13.26+ / 15+, `chan_pjsip`):

```ini
[gsm-outbound]
; Агент звонит на номер абонента в международном формате (+4915...).
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,PJSIP_INHERITABLE_HEADER(add,X-GSM-Forward)=${GW_DEST}
 same => n,Dial(PJSIP/1001,60)
 same => n,Hangup()
```

**Вариант B — pre-dial-обработчик** (любая версия, где есть `b()` в `Dial()`):

```ini
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,Dial(PJSIP/1001,60,b(add-gsm-forward^s^1))
 same => n,Hangup()

; В pre-dial-обработчике PJSIP_HEADER(add,...) работает с каналом
; ВЫЗЫВАЕМОГО — поэтому заголовок уезжает в INVITE, который уходит шлюзу.
[add-gsm-forward]
exten => s,1,Set(PJSIP_HEADER(add,X-GSM-Forward)=${GW_DEST})
 same => n,Return()
```

Проверить, что нужное приложение есть:

```bash
asterisk -rx "core show application PJSIP_INHERITABLE_HEADER"
```

### 2.2 GSM → PBX (абонент звонит на SIM, шлюз звонит в PBX)

При входящем GSM-вызове шлюз сам отправляет INVITE на **собственный номер
SIM** в международном формате (`+4915112345678`), который настроен в
приложении (Settings → «Own number») или читается с SIM. Номер вызывающего
идёт в `From` (и в `P-Asserted-Identity`, если PBX его добавляет).

Запрос приходит на зарегистрированный эндпоинт `1001`, поэтому его контекст
должен быть `from-gsm-gateway`.

```ini
[from-gsm-gateway]
; To в INVITE = <sip:+4915112345678@pbx> — это собственный DID шлюза.
exten => _+X.,1,NoOp(GSM gateway: inbound from ${CALLERID(num)})
 same => n,Set(GW_FROM=${CALLERID(num)})
 same => n,Set(GW_FROM=${GW_FROM:0})        ; если транк ждёт номер без "+"
 same => n,Dial(PJSIP/trunk-name/${GW_FROM},60)
 same => n,Hangup()
```

`${CALLERID(num)}` на PJSIP-канале — это user-часть `From`, то есть номер
GSM-вызывающего. Если PBX добавляет `P-Asserted-Identity`, его можно читать и
явно: `${PJSIP_HEADER(read,P-Asserted-Identity)}` — шлюз тоже смотрит в него
первым.

### 2.3 Кто такой вызывающий в `From` и почему это важно

Шлюз пишет в `From` **номер GSM-вызывающего**, а не имя аккаунта:

```
From: <sip:+4915112345678@pbx>;tag=...
```

Для обычных звонков это не мешает: `res_pjsip` сопоставляет запрос с
эндпоинтом по зарегистрированному AOR (по contact'у), а не по user-части
`From`. Проблема возникает, когда запрос приходит не с адреса регистрации —
например, за NAT с другим публичным адресом, либо для `MESSAGE` (SMS), где
регистрации вовсе нет. Для таких случаев нужен `identify` по адресу
источника (см. §5), и вот он как раз ломается при динамическом адресе.

Комбинация `identify` + `message_context` нужна только для исходящего
`MESSAGE` (SMS) — в рамках этой задачи (звонки) она не требуется.

## 3. Требования к pjsip.conf

Если вы работаете через веб-панель FreePBX, создайте расширение
**Administration → Extensions → Add Extension → Device** с этими значениями:

| Поле | Значение |
|---|---|
| Extension Number | `1001` |
| Device Type | Device |
| Secret / Password | пароль шлюза |
| Context | `from-gsm-gateway` (см. §4) |
| Advanced → Codecs | `g722` и `alaw`/`ulaw` (см. §6) |
| Advanced → Transports | UDP или TLS (см. §5) |
| Advanced → Outbound Proxy | пусто (шлюз регистрируется к нам, не наоборот) |
| Advanced → RTP → Direct Media | No |

Готовые файлы конфигурации:

```ini
; /etc/asterisk/pjsip.conf

; Транспорты. Приложение умеет только UDP и TLS — «голого» SIP поверх TCP
; в нём нет, и эндпоинт с transport=tcp не зарегистрируется.
[transport-udp]
type=transport
protocol=udp
bind=0.0.0.0:5060

[transport-tls]
type=transport
protocol=tls
bind=0.0.0.0:5061
tls_cert_file=/etc/asterisk/keys/asterisk.crt
tls_key_file=/etc/asterisk/keys/asterisk.key

[1001]
type=endpoint
; Контекст входящих вызовов от шлюза (и звонков на 1001 от агентов).
context=from-gsm-gateway
transport=transport-udp
; Медиа не шоркаутим: Asterisk — B2BUA, RTP между агентом и шлюзом идёт
; через Asterisk, шлюз держит вторую ногу (сотовую) сам.
; Прямой медиа запрещён ещё и потому, что шлюз не пересогласовывает медиа
; по re-INVITE и продолжает слать RTP на запомненный адрес.
direct_media=no
; Кодеки. Шлюз по умолчанию предлагает 9 8 0 101:
;   9 = G722, 8 = PCMA (A-law), 0 = PCMU (µ-law), 101 = telephone-event.
; Эндпоинт обязан разрешать хотя бы один аудиокодек из предложения шлюза,
; иначе предложение неприемлемо и звонок не состоится.
allow=!all,g722,alaw,ulaw
; Регистрация шлюза с digest-аутентификацией.
authenticate=yes
aors=1001
callerid=GSM Gateway
; Не отвечать 180 раньше времени: шлюз сам сообщает 180, когда пошла
; сотовная нога.
; SRTP по умолчанию не включаем: G.722 + TLS достаточно, а SRTP добавляет
; согласование ключей, которое придётся проверять отдельно.
; Включать, если транк требует:
;media_encryption=sdes
;media_encryption=dtls
; Свои SIP-заголовки не отбрасываем.
allow_transfer=yes

[1001]
type=aor
max_contacts=1
remove_existing=yes
qualify_frequency=60

[1001]
type=auth
auth_type=userpass
username=1001
password=CHANGE_ME_STRONG_PASSWORD
```

Идентификаторы `1001` в секциях `endpoint`/`aor`/`auth` — одинаковые имена
секций в PJSIP допустимы (это разные типы), но во FreePBX UI они
создаются автоматически.

## 4. `extensions.conf` — маршрутизация

```ini
; /etc/asterisk/extensions.conf

; ── Исходящий: агент звонит абоненту через сотовную ногу шлюза ──
; Контексты и приложения — см. §2.1.
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Set(GW_DEST=${EXTEN})
 same => n,Dial(PJSIP/1001,60,b(add-gsm-forward^s^1))
 same => n,Hangup()

[add-gsm-forward]
exten => s,1,Set(PJSIP_HEADER(add,X-GSM-Forward)=${GW_DEST})
 same => n,Return()

; ── Входящий: абонент звонит на SIM, шлюз звонит в PBX ──
; См. §2.2.
[from-gsm-gateway]
exten => _+X.,1,NoOp(GSM gateway: inbound from ${CALLERID(num)})
 same => n,Set(GW_FROM=${CALLERID(num)})
 same => n,Set(GW_FROM=${GW_FROM:0})
 same => n,Dial(PJSIP/trunk-name/${GW_FROM},60)
 same => n,Hangup()

; Прямые звонки на 1001 от агента (номер абонента передаётся в аргументе):
;   1001 + 79001234567 → агент звонит на 100179001234567
exten => _1001X.,1,NoOp(GSM gateway: agent dialled the gateway with a number)
 same => n,Set(GW_DEST=${EXTEN:4})
 same => n,Goto(gsm-outbound,${GW_DEST},1)
```

### Про `Dial()` и таймаут

Для GSM-замыкания нужно **не меньше 60 секунд**: время установки сотовной
ноги (дозвон, ответ абонента) существенно больше длительности SIP-транзакции.
20 секунд — недостаточно, разрыв будет выглядеть как таймаут.

## 5. `identify` и адрес шлюза

Если запросы от шлюза не сопоставляются с эндпоинтом по регистрации
(`No matching endpoint found`), добавьте сопоставление по адресу источника:

```ini
; /etc/asterisk/pjsip.conf
[1001]
type=identify
endpoint=1001
match=192.168.1.10
```

Оговорки:

- адрес должен быть **статическим**: за динамическим адресом (DHCP) или за
  NAT, где внешний адрес меняется, `identify` перестаёт совпадать и запросы
  снова не находятся;
- для обычных звонков `identify` не нужен — хватает совпадения по
  зарегистрированному contact'у;
- `message_context` в связке с `identify` нужен только для исходящего
  `MESSAGE` (SMS) — это вне рамок задачи «звонки».

## 6. Кодеки

**Поведение изменено:** по умолчанию шлюз предлагает
`9 8 0 101` — G.722, PCMA (A-law), PCMU (µ-law) и telephone-event. Раньше
по умолчанию предлагался только G.722 (`9 101`), и эндпоинт, разрешающий
только `alaw`/`ulaw`, отвечал на это `488 Not Acceptable` — звонок не
начинался вовсе.

Что это значит для конфигурации:

| `allow` на эндпоинте | Что выберет Asterisk | Результат |
|---|---|---|
| `!all,g722,alaw,ulaw` | G.722 (его порядок предпочтений первый) | широкополосный RTP (16 кГц); имеет смысл только при AMR-WB на сотовной стороне |
| `!all,alaw,ulaw` | PCMA (A-law) | узкополосный RTP (8 кГц) — совпадает с сотовной ногой (AMR-NB) и гарантирован транком |
| `!all,ulaw` | PCMU (µ-law) | узкополосный RTP (8 кГц), µ-law |

Кодек выбирает **Asterisk**, по своему порядку `allow`, а не шлюз; шлюз
подстраивается под ответ. Ответ `200 OK` теперь перечисляет только
согласованный payload (например `m=audio 5000 RTP/AVP 8 101`), поэтому
предложение и ответ всегда согласованы и оба конца используют один кодек.

Если нужен строго G.722, выберите в приложении Settings → Codec режим
«G.722 only»: тогда предложение шлюза будет `9 101`, и эндпоинт должен
разрешать `g722`. Обратная сторона «по умолчанию всё» — если сервер
предпочитает G.711, разговор останется узкополосным; для сотовной ноги это
не цена: она и так 8 кГц.

## 7. Требования к TLS

Приложение проверяет цепочку сертификатов **и** имя хоста, и не имеет опции
«доверять всем» (иначе пароль от регистрации ушёл бы кому попало). Отсюда:

- нужен FQDN, совпадающий с SAN сертификата; подключение по IP не сработает;
- сертификат должен выдавать CA, которому доверяет телефон. Варианты:
  1. публичный CA (Let's Encrypt) на имени, доступном телефону — проще всего;
  2. собственный CA, установленный в хранилище доверия телефона
     (для рутованного телефона — системный CA через Magisk-модуль,
     `/system/etc/security/cacerts/<hash>.0`).

На стороне PBX:

```bash
# TLS-слушатель должен быть включён и иметь сертификат
asterisk -rx "pjsip show tls"
asterisk -rx "pjsip show transports"
```

В `http.conf` TLS-слушатель Asterisk берётся из `asterisk.conf`:

```ini
[options]
tlscertfile = /etc/asterisk/keys/asterisk.crt
tlskeyfile  = /etc/asterisk/keys/asterisk.key
```

После правки: `asterisk -rx "pjsip set tls on"`.

## 8. Проверка на сервере

```bash
# Регистрация шлюза
asterisk -rx "pjsip show registrations"
asterisk -rx "pjsip show endpoint 1001"

# Входящий INVITE от шлюза: должен попасть в контекст from-gsm-gateway
asterisk -rx "dialplan show from-gsm-gateway"

# Живой вызов: смотрим заголовок на входящем INVITE
grep -E "X-GSM-Forward" /var/log/asterisk/full

# Исходящий: заголовок на канале к шлюзу и согласованный кодек
asterisk -rx "pjsip show channelstats"
```

Типичные ошибки:

| Симптом | Причина |
|---|---|
| `No matching endpoint found` | Регистрация не прошла или contact не совпадает; проверьте `pjsip show registrations`. Если адрес шлюза меняется — см. §5 про `identify` |
| Шлюз отвечает `488` | В INVITE нет `X-GSM-Forward`, а user-часть Request-URI не похожа на номер — шлюзу нечего dial'ить |
| Заголовок `X-GSM-Forward` не видно в `full` | `PJSIP_HEADER(add,...)` в обычном контексте добавляет его вызывающему каналу и не наследуется в INVITE от `Dial()` — нужен `PJSIP_INHERITABLE_HEADER` либо pre-dial-обработчик (§2.1) |
| Звонок идёт, но через ~20 с обрывается | Слишком короткий `Dial()` — поставьте 60 |
| Звонок идёт, звука нет, в `channelstats` другой кодек | Эндпоинт разрешает не тот кодек, который согласован; сверьте `allow` с §6 |
| Входящий от SIM не маршрутизируется | Контекст эндпоинта не `from-gsm-gateway` либо `Dial()` уходит не в тот транк |

## 9. Замечания по RTCP

Шлюз не реализует RTCP и не объявляет `a=rtcp` в своём SDP. RTCP-трафик
Asterisk уходит на порт RTP + 1 и остаётся без ответа. На передачу голоса
это не влияет: RTCP не несёт звука, а таймаут RTP на стороне Asterisk
задаётся отдельно (`rtp_timeout` / `rtp_timers=yes`).

## 10. Что нужно от оператора сотовой связи

- Номер SIM должен принимать входящие вызовы (для направления GSM → SIP).
- Номер должен быть в E.164; он же используется как DID шлюза в направлении
  GSM → PBX (см. §2.2).
- Если SIM заведена с **VoWiFi (WFC)** — его нужно отключить: в режиме WFC
  сотовной ноги нет, модемного аудио-канала не существует, мост невозможен.
- При **VoLTE/IMS** голос идёт пакетным вызовом; работает ли аудио-мост на
  IMS-вызове, проверяется на живом вызове (см. `docs/DEPLOYMENT.md`).
