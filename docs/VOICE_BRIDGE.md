# Голосовой мост на Cubot X100 (MT6855): как телефон оказался участником разговора

Разбор и исправление, 2026-11-19. Все утверждения — наблюдения на устройстве
(`tinymix`, `dumpsys media.audio_policy`, `logcat`) и в коде проекта.

## 1. Симптом

В разговоре, который идёт через шлюз:

* в динамике телефона слышен разговор — он дублируется в помещении;
* микрофон телефона тоже участвует в разговоре.

То есть телефон, на котором стоит шлюз, оказался не мостом, а участником
разговора.

## 2. Почему так вышло

### 2.1 Мост был акустическим

Цифрового маршрута на этом устройстве не было: аудио агента игралось
**обычным `AudioTrack` в динамик**, а сотовый абонент слышал агента только
потому, что **микрофон телефона** подхватывал этот звук и уносил его в
сотовый аппарат (сотовая нога — акустический контур). Отсюда оба симптома
сразу: звук в помещении и микрофон в разговоре.

### 2.2 Почему не нашёлся цифровой маршрут

Цифровая инъекция на этом чипе есть, и она объявлена в политике аудио:

```xml
<!-- /vendor/etc/audio_policy_configuration.xml -->
<mixPort name="incall_music_uplink" role="source" flags="AUDIO_OUTPUT_FLAG_INCALL_MUSIC">
    <profile name="" format="AUDIO_FORMAT_PCM_16_BIT"
             samplingRates="44100 48000" channelMasks="AUDIO_CHANNEL_OUT_STEREO"/>
</mixPort>
...
<devicePort tagName="Telephony Tx" type="AUDIO_DEVICE_OUT_TELEPHONY_TX" role="sink">
...
<route type="mix" sink="Telephony Tx"
       sources="Built-In Mic, ..., incall_music_uplink"/>
```

Трек, которому назначено устройство `Telephony Tx`, попадает в mixPort
`incall_music_uplink`, а тот — в микс `Telephony Tx`, то есть **прямо в
аппаратный аплинк модема**.

Проба (`MediaTekCapabilityProbe`) искала порт так:

```kotlin
private val DEVICEPORT_TX = Regex("""devicePort name="Telephony Tx"""")
```

а в этом policy атрибут называется **`tagName`**, а не `name`. Регулярка не
совпала → проба сообщила «нет порта Telephony Tx» → планировщик выбрал
маршрут BGS (background-sound player), параметры которого HAL на этом
поколении принимает, но **никогда не подтверждает** — а значит, и не
применяет. Итог: цифровой маршрут был в устройстве, но приложение его не
видело и уходило в акустический контур.

### 2.3 Микрофон оставался в разговоре

Муты пишутся один раз, на старте вызова (`mixerSetupCmd`), а HAL
**переписывает их**, когда программирует голосовой путь. Поэтому записанный
заранее мут снимался, и микрофон возвращался в разговор. В проекте это уже
описано для других чипов — и там мут пишется повторно, после того как HAL
успокоился. Для MediaTek-профилей повторного мутa не было (`mixerIncallMusicCmd`
пуст).

Кроме того, в микшере есть ещё один контрол, который никто не трогал:

```
Speech_Mic_Mute   BOOL   Off      ← микрофон в голосовом пути
Speech_UL_Mute    BOOL   Off      ← микрофон в сотовом аплинке
Speech_DL_Mute    BOOL   Off      ← downlink модема в динамик
```

`Speech_UL_Mute` глушит микрофон в **сотовом** аплинке, `Speech_Mic_Mute` — в
**голосовом** пути, откуда приложение снимает абонента. Для шлюза нужны оба.

### 2.4 Параметры BGS ни разу не применялись

В профиле есть `halCallParams = MediaTekBgs.CALL_PARAMS` (это
`Set_BGS_UL_Mute=0` / `Set_BGS_DL_Mute=1` — «влить агента в аплинк, не играть
в динамик»), но поле **нигде не читается**: grep по проекту показывает
только определение и присваивания. Мёртвый код.

## 3. Что сделано

| # | Изменение | Файл |
|---|-----------|------|
| 1 | Проба принимает и `name`, и `tagName` у devicePort | `mediatek/MediaTekCapabilityProbe.kt` |
| 2 | При неподтверждённых BGS-параметрах и объявленном `incall_music` выбирается цифровой маршрут | `mediatek/MediaTekCapabilities.kt` |
| 3 | Профиль `INCALL_MUSIC`: `digitalBridge = true`, мут микрофона | `mediatek/MediaTekProfiles.kt` |
| 4 | Новый профиль-флаг `digitalBridge` и команда `mixerHandsetMuteCmd` | `DeviceProfile.kt` |
| 5 | Трек уводится на устройство `Telephony Tx` (USAGE_MEDIA, стерео), а не в динамик | `rtp/RtpSession.kt` |
| 6 | Мут микрофона пишется после того, как HAL программирует голосовой путь, вместе с readback | `rtp/RtpSession.kt`, `mediatek/MediaTekCapabilities.kt` |
| 7 | Уровень агента в аплинке — 100 % (поток `STREAM_MUSIC` теперь несёт инъекцию, а не динамик) | `mediatek/MediaTekProfiles.kt` |
| 8 | Переключатель «Digital bridge» в настройках + `Speech_Mic_Mute` в восстановление | `MainActivity.kt`, `res/layout/activity_main.xml` |

Переключатель «Digital bridge» (вкл. по умолчанию) — это страховка: если
политика аудио конкретного устройства не предложит маршрут в `Telephony Tx`,
сотовная сторона замолчит (микрофон заглушён, а инъекции нет). Выключатель
возвращает акустический контур.

## 4. Как проверить

Живой вызов, обе стороны говорят. В логе телефона ожидается:

```
Digital bridge: true (profile=MT6855 (MediaTek) INCALL_MUSIC / VOICE_DOWNLINK)
Track routed: device=... rate=... channels=2
Handset mutes: Speech_UL_Mute=On Speech_Mic_Mute=On Speech_DL_Mute=...
```

и в RTP-статистике ненулевой `capRMS` (абонент слышен агенту) и ненулевой
`playRMS` (агент играется в аплинк).

Что должен подтвердить человек на сотовой стороне:

1. агент слышен, без эха и без шума помещения;
2. в динамике телефона **ничего** не слышно;
3. агент слышит абонента, без голоса из помещения.

Если сотовная сторона молчит — выключить «Digital bridge» и разбираться
дальше (см. §5).

## 5. Что осталось проверить

* `Speech_DL_Mute` в команде мутов намеренно **не** переписывается: не
  доказано, что он не глушит `VOICE_DOWNLINK`-захват (иначе агент перестал бы
  слышать абонента). Если после исправления в динамике слышно голос
  абонента (downlink модема), мут нужно добавить — отдельной проверкой.
* Параметры `halCallParams` (BGS) остались мёртвым кодом: на этом поколении
  они не работают, а чинить их нужно с тестом на MT6753.

## 6. Итерация 2: замер живого звонка (16:28:46)

Первый тест после §3. Лог телефона:

```
Digital bridge: true (profile=MT6855 (MediaTek) INCALL_MUSIC / VOICE_DOWNLINK)
RTP: incall_music: param=incall_music_enabled, mode=2
Preferred device -> TELEPHONY id=13 accepted=true
Track routed: device=18/X100 rate=8000 channels=2
Handset mutes: Speech_UL_Mute: On
RTP: tx=662 rx=652 play=646 capRMS=0 rawCapRMS=0 playRMS=8
RTP: Dead air 6s on VOICE_DOWNLINK (source proven — keeping it)
```

Что подтвердилось:

* **цифровая инъекция работает** — трек уведён на устройство `Telephony Tx`
  (тип 18), HAL принял `incall_music_enabled`, агент слышен абоненту, и его
  голос больше не идёт через микрофон телефона;
* **захват мёртв** — `capRMS=0 rawCapRMS=0` весь звонок: агент не слышит
  абонента.

### 6.1 Почему захват мёртв

`AudioRecord` с `AudioSource.VOICE_DOWNLINK` на этом HAL инициализируется и
даёт нули:

```
AudioRecord OK: VOICE_DOWNLINK @ 8000Hz (buf=640)
Capture routedFrom=18          ← привязан к telephony-устройству
```

То есть маршрут есть, сигнала нет. Других цифровых путей на устройстве нет:
`telephonyRxPcm=null` (нечего читать tinycap'ом), а `VOICE_CALL` был **вычеркнут
из цепочки источников** профилем: при `voiceDownlinkWorks=true` код убирает его
и ставит `VOICE_DOWNLINK` первым — а тот на этом чипе молчит. Плюс
`silenceFallback=false` запрещал детектору тишины снять мёртвый источник:
в логе так и написано — «source proven — keeping it».

Итог: **в направлении GSM → PBX агент слышит тишину.** Это было и до правок
(в замере 15:29 те же нули), то есть не регрессия, а неучтённый дефект.

### 6.2 Что изменено в итерации 2

| # | Изменение | Зачем |
|---|-----------|-------|
| 1 | `Speech_DL_Mute=1` добавлен в команду мутов (перезапись после HAL) | голос абонента из downlink модема больше не звучит в динамике телефона |
| 2 | `VOICE_CALL` остаётся в цепочке источников при включённом цифровом мосте | аплинк чист (агент идёт в модем цифрой, микрофон не участвует), а на этом чипе это единственный источник, который вообще несёт абонента |
| 3 | `silenceFallback = true` для MediaTek-профилей | источник, который молчит, снимается детектором тишины, и цепочка идёт дальше, а не держит мёртвый захват весь звонок |

### 6.3 Что ждём от следующего теста

В логе ожидается смена источника захвата и ненулевой `capRMS`:

```
AudioRecord OK: VOICE_CALL @ 8000Hz
RTP: … capRMS=… rawCapRMS=…
```

и вопросы те же:

1. слышит ли абонент агента (без эха);
2. слышно ли что-нибудь в динамике телефона;
3. **слышит ли агент абонента** — и нет ли в голосе агента шума из помещения
   (если `Speech_Mic_Mute` не вывел микрофон из голосового пути, в захвате
   будет комната).

Если после `Speech_DL_Mute=1` захват окажется немым — значит этот мут
глушит и downlink в пути захвата; тогда его придётся убрать и глушить
динамик иначе (на этом чипе другого контрола нет).

## 7. Итерация 3: почему телефон всё ещё был в разговоре (17:03)

Итерация 2 починила захват (`capRMS=52`, `src=VOICE_CALL`), но телефон по
прежнему слышал абонента в динамике, а микрофон оставался в разговоре.
Разбор — по логу звонка 16:39, логам APM/AudioFlinger и строкам HAL.

### 7.1 Инъекция цифровая — телефон в разговоре по другой причине

Конец звонка в логе APM показывает, куда ушёл наш трек:

```
[MTK_APM_Output]releaseOutput() 53 portId 213
disconnectAudioSource, PortId: 213 SessionId: 0 Uid: 1041 Stream: 13
[MTK_APM_Route]setOutputDevices() mIoHandle 53 mId 12 device (0x10000)
```

* `ioHandle 53` — mixPort `incall_music_uplink`;
* `Stream: 13` — `STREAM_MUSIC` (трек приложения), `Uid 1041` — наш пакет;
* `mId 12` — устройство `Telephony Tx`, `device 0x10000` =
  `AUDIO_DEVICE_OUT_TELEPHONY_TX`.

Значит голос агента уходит **в аплинк модема**, а не в динамик. То, что слышно
в динамике телефона, — это **собственный downlink модема** в ухо/динамик
аппарата: отдельный путь, который шлюз своим треком не занимает.

### 7.2 Профиль вообще не просил телефон замолчать

Лог 16:39 — строка `enforceVolumes`:

```
Vol: voice=7(m=false), music=15/15(target=15)
```

Голосовой поток не заглушён (7 из 15) — значит, в динамике звучит абонент.
Профиль `INCALL_MUSIC` имел `silenceLocalAudio = false`, поэтому
`enforceVolumes` уходил в ветку «акустика»: громкость голоса 70 %, а
`am.isMicrophoneMute = false` — микрофон **явно** разблокирован
(`GsmCallManager.kt`: `if (!profile.silenceLocalAudio) am.isMicrophoneMute = false`).

Это и есть корень: цифровая инъекция была, а «убери телефон из разговора»
никто не выполнял.

### 7.3 Микшерные муты на VoLTE-пути не действуют

Муты писались и читались как `On`:

```
Handset mutes: Speech_UL_Mute: On / Speech_Mic_Mute: On / Speech_DL_Mute: On
```

и всё равно абонент был слышен. Значит `Speech_UL_Mute` / `Speech_DL_Mute` /
`Speech_Mic_Mute` управляют **старым** речевым путём (SHM, 2G/3G), а на этом
устройстве голос идёт через DSP, и эти контролы к нему отношения не имеют.

### 7.4 У HAL есть свой мут — и мы в него не заходили

Строки `audio.primary.mediatek.so` (это тот же бинарник, что и
`audio.primary.mt6855.so`):

```
Set_SpeechCall_DL_Mute          Set_SpeechCall_UL_Mute
Set_SpeechCall_Dynamic_DL_Mute  Set_BGS_DL_Mute   Set_BGS_UL_Mute
… %s(), mDlMute: %d => %d   %s(), mMicMute: %d => %d
… mUplinkMuteOn %d, mUplinkSourceMuteOn %d, mDownlinkMuteOn %d
```

HAL держит **собственное** состояние мута (`mDlMute`, `mMicMute`) и меняет его
только своими параметрами. `halCallParams` в профиле для этого семейства был
пуст — параметры не отправлялись никогда.

### 7.5 Что изменено в итерации 3

| # | Изменение | Файл |
|---|-----------|------|
| 1 | MediaTek-профили с цифровым мостом: `silenceLocalAudio = true` | `mediatek/MediaTekProfiles.kt` |
| 2 | Ветка «цифровой мост» в `enforceVolumes` глушит `STREAM_VOICE_CALL` (абонент в динамике) и микрофон (`isMicrophoneMute`), с readback в лог | `gsm/GsmCallManager.kt` |
| 3 | Поток `STREAM_MUSIC` (носит инъекцию) сохраняет свой уровень — агент слышен абоненту | `gsm/GsmCallManager.kt` |

Глушение идёт **через фреймворк**, а не через микшер: `AudioManager` работает
с HAL, который и обслуживает голосовой путь. Микшерные муты оставлены как
второй слой.

Ожидаемый след в логе:

```
Local audio silenced: voiceMute=true micMute=true music=15/15(target=15)
```

### 7.6 Что делать, если фреймворк-мут не дойдёт до модема

Тогда следующий слой — **HAL-параметры** (они есть в бинарнике HAL, §7.4):

```
Set_SpeechCall_DL_Mute=1     # downlink модема в динамик
Set_SpeechCall_UL_Mute=1     # микрофон в сотовом аплинке
```

Их нужно отправлять через `AudioManager.setParameters(...)` — в проекте это
`profile.halCallParams`, механизм есть, но для этого семейства список был
пустым.

Опасность: `Set_SpeechCall_UL_Mute` может глушить **весь** аплинк вместе с
инъекцией (HAL различает `mUplinkMuteOn` и `mUplinkSourceMuteOn`), поэтому его
включать последним и обязательно с проверкой, что абонент по-прежнему слышит
агента.

Третий рычаг — микшерный контрол **`Handset Volume`** (уровень голоса в
динамике, сейчас 0) и `Lineout Volume` (уровень аплинка, 31 31): ими можно
добить, если HAL-параметры не помогут.

## 8. Итерация 3: живой тест 17:08 — мут микрофона убил обе стороны

Сборка 17:03 (первая с `silenceLocalAudio = true`) поставлена на телефон,
звонок 17:08:17 → 17:08:41. Что показал телефон:

```
Local audio silenced: voiceMute=true micMute=true music=15/15(target=15)
AudioRecord OK: VOICE_CALL @ 8000Hz
AudioRecord OK: VOICE_DOWNLINK @ 8000Hz (fallback=0 attempt=1)
RTP: … capRMS=0 rawCapRMS=0 playRMS=8 src=VOICE_DOWNLINK
AudioRecord OK: VOICE_RECOGNITION @ 8000Hz (fallback=1 attempt=1)
```

Человек на сотовой стороне подтвердил: **в динамике телефона стало тихо** (цель
достигнута), но одновременно **пропал звук на софтфоне и пропал микрофон
абонента** — то есть услышали мышишь.

### 8.1 Что именно сломалось

`capRMS=0` — захват мёртв. Цепочка источников откатилась
`VOICE_CALL → VOICE_DOWNLINK → VOICE_RECOGNITION` (микрофон!), потому что
детектор тишины снял первый источник через 3 с.

Причина — мут микрофона **через фреймворк** (`am.isMicrophoneMute = true` плюс
`Telecom.setMuted(true)`). На этом чипе такой мут снимает **весь голосовой
путь**, а не только источник микрофона:

* агент перестал слышать абонента — погиб `VOICE_CALL` (DL модема);
* абонент перестал слышать агента — погиб аплинк, в который идёт цифровая
  инъекция (`incall_music_uplink → Telephony Tx`).

То есть на MT6855 мут микрофона — это не «выключить один источник», а
«выключить голос вообще». Для шлюза это неприемлемо: голос агента и голос
абонента идут по одному и тому же пути.

### 8.2 Что изменено в итерации 3

| # | Изменение | Файл |
|---|-----------|------|
| 1 | Новый флаг профиля `frameworkMicMuteSafe` (по умолчанию `true`, для MediaTek — `false`) | `DeviceProfile.kt` |
| 2 | MediaTek-профили: `frameworkMicMuteSafe = false` — мут микрофона через фреймворк и Telecom-мут не применяются | `mediatek/MediaTekProfiles.kt`, `gsm/GsmCallManager.kt` |
| 3 | Глушение динамика вынесено из `enforceVolumes` в отдельный `muteLocalVoiceOutput()` и применяется **после** того, как захват пошёл | `gsm/GsmCallManager.kt` |
| 4 | `RtpSession` глушит динамик на 3-й секунде звонка, передавая в лог уровень захвата «до» | `rtp/RtpSession.kt` |

Пункт 3 — это и измерение, и страховка: если на каком-то чипе глушение
голосового потока тоже утащит голосовой путь, это будет видно в логе
(`capRMS before=…` → следующая статистика), а не молча убьёт агента.

Микрофон при этом остаётся вне разговора за счёт ALSA-контрола
`Speech_UL_Mute` (он снимает именно источник микрофона в сотовом аплинке и
не трогает цифровую инъекцию) — это проверяется следующим тестом: если
абонент услышит комнату, значит `Speech_UL_Mute` на VoLTE-пути не работает и
нужен HAL-параметр `Set_SpeechCall_UL_Mute=1` (риск: он может глушить весь
аплинк вместе с инъекцией — проверять последним).

## 9. Итерация 4 (17:17): `VOICE_CALL` на MT6855 несёт только аплинк

Тест 17:17 — уже без мутов микрофона через фреймворк. Результат:

```
Local voice output muted: capRMS before=13 muted=true
RTP: … capRMS=18  src=VOICE_CALL
RTP: … capRMS=1089 src=VOICE_CALL
```

Человек на сотовой стороне: **в динамике телефона тихо** (цель достигнута),
голос агента доходит до абонента (инъекция жива), но **абонента не слышно
совсем**, а на софтфоне слышно «звук с микрофона кубота».

### 9.1 Что это значит

`VOICE_CALL` на этом чипе отдаёт **аплинк**: микрофон (плюс собственная
инъекция голоса агента — поэтому агент слышит себя). Downlink модема в потоке
нет. Это совпадает с описанием в апстриме проекта (`pulpoff/gsm2sip`,
README, раздел MediaTek):

> *Agent hears itself / heavy noise: capture must use `VOICE_DOWNLINK`, not
> `VOICE_CALL`. The latter mixes uplink and downlink, and the uplink carries
> the injected agent audio.*

То есть «микрофон кубота на софтфоне» — это эхо собственной инъекции плюс
комната. **Абонент не был слышен ни в одном из предыдущих прогонов**; просто
раньше это выглядело как «шум помещения».

### 9.2 Где искать downlink

* `AudioSource.VOICE_DOWNLINK` — на MT6855 открывается, но читает нули:
  в политике нет маршрута от устройства `Voice Call In`
  (`AUDIO_DEVICE_IN_TELEPHONY_RX`) ни в один **входной** mixPort — только в
  выходные (`Earpiece`, `Speaker`, …). Захватывать нечего.
* ALSA-карта `mt6855-mt6369` содержит отдельный PCM:

  ```
  00-60: VOW_Capture mt6369-snd-codec-vow-60
  ```

  Это голосовой путь модема в домене кодека — прямой доступ к разговору
  через root, тем же способом, каким апстрим читает telephony-rx PCM на
  Pixel 7 (`tinycap`).

* HAL-параметры `Set_SpeechCall_UL_Mute=1` / `Set_SpeechCall_DL_Mute=1` —
  так апстрим глушит MediaTek-телефон (не микшером: микшерные муты HAL
  переписывает).

### 9.3 Сбой, который выглядел как «ошибка при наборе» (17:43)

Звонок оборвался не по аудио, а потому, что система убила приложение:

```
17:42:55  PermissionController → ManagePermissionsActivity (экран прав в фокусе)
17:43:04.971  ActivityManager: Killing com.callagent.gateway (adj 50): permissions revoked
17:43:16  сервис перезапущен, права перевыданы, регистрация восстановлена
```

И в этом виноват сам шлюз: код восстановления appops (`reAssertAppOps`)
убивает `PermissionController`, чтобы тот переприменил UID-режим; перезапустившийся
`PermissionController` прогоняет синхронизацию политики прав, и пакет с
отозванным правом система убивает — вместе с живым звонком.

Правка: `kill PermissionController` выполняется **только когда звонка нет**
(`rtp/RtpSession.kt`, `service/GatewayService.kt`,
`bridge/CallOrchestrator.kt`). UID-режим и так ставится напрямую через
`appops set --uid`.

## 10. Итерация 5: что именно убивает downlink модема

Тест 17:50 — снят микшерный `Speech_DL_Mute` (он всё равно не работал) и
заменён на глушение голосового потока через фреймворк. Лог:

```
17:50:35.272  Local voice output muted: capRMS before=2483 muted=true
17:50:40.332  RTP: … capRMS=101  rawCapRMS=101 src=VOICE_CALL
17:50:45.394  RTP: … capRMS=15   rawCapRMS=15  src=VOICE_CALL
```

`capRMS before=2483` — **голос абонента в захвате был**, и он исчез ровно в
момент, когда применился мут голосового потока. Человек на сотовой стороне:
«звука нет совсем в обе стороны».

Вывод: **на этом чипе любой мут голосового пути уносит downlink модема из
захвата агента.** Мутят ли его и в динамике одновременно — неважно, важен
факт: обе точки, которые мы использовали, убивают вторую половину моста.

| Рычаг | Что делает | Годится? |
|---|---|---|
| `tinymix 'Speech_DL_Mute' 1` | микшерный, старое поколение; HAL переписывает | нет — и в динамик не глушит, и из захвата убирает |
| `AudioManager.STREAM_VOICE_CALL` mute | голосовой поток фреймворка | нет — уносит downlink из захвата |
| `AudioManager.isMicrophoneMute` | микрофон фреймворка | нет — уносит весь голосовой путь (замер 17:08) |
| `Set_SpeechCall_DL_Mute=1` | HAL-параметр вендора | нет — тот же голосовой путь |
| `Set_SpeechCall_UL_Mute=1` | HAL-параметр вендора | не проверен: глушит весь аплинк вместе с инъекцией |

### 10.1 Чем глушить динамик, не убивая мост

**Выход устройства, а не голосовой путь.** В `/vendor/etc/audio_device.xml`:

```xml
<path name="receiver_output" value="turnon">
    <kctl name="RCV Mux" value="Voice Playback" />   ← абонент в ухе
<path name="receiver_output" value="turnoff">
    <kctl name="RCV Mux" value="Open" />              ← тишина
<path name="dual_speaker_output" value="turnon">
    <kctl name="LOL Mux" value="Playback" />          ← абонент в динамике
```

`RCV Mux` / `LOL Mux` — это пути **выхода** кодека (ухо и динамик). Их глушение
не касается пути модема, который читает агент. Поэтому:

* `mixerHandsetOutputMuteCmd` (новое поле профиля) = `RCV Mux Open` + `LOL Mux Open`;
* применяется **поздно** (через 3 с после старта захвата) и **переподтверждается**
  на каждом цикле статистики — HAL переписывает эти контролы, когда
  программирует голосовой путь и когда переключает выходное устройство;
* в лог идёт уровень захвата «до» — если мут всё-таки утащил бы путь, это
  было бы видно сразу.

### 10.2 Побочная находка: `VOW_Capture` недоступен во время звонка

PCM `00-60: VOW_Capture mt6369-snd-codec-vow-60` — отдельный голосовой путь
модема в домене кодека, идеальный кандидат на цифровой захват. Но он
принадлежит HAL: при попытке открыть его во время звонка чтение падает с
`read error: File descriptor in bad state`, и голосовой путь модема при этом
ломается — звонок остаётся без звука в обе стороны. Прямой доступ к нему
невозможен, пока HAL держит путь; закрыт.

### 10.3 Что ждём от теста

1. агент слышит абонента (в захвате снова голос абонента);
2. в динамике/ухе телефона тихо (мут выхода сработал);
3. абонент слышит агента (инъекция в аплинк не сломана).

Микрофон телефона — отдельный вопрос: он выводится из сотового аплинка
микшерным `Speech_UL_Mute` (поуровневый, инъекцию не трогает). Проверяется
тем, что абонент не слышит комнату; если слышит — нужен вендорский
`Set_SpeechCall_UL_Mute=1`, но его придётся вводить последним и проверять,
что инъекция выжила.

## 11. Итерация 6 (19:03 и 19:12): вендорский `Set_SpeechCall_UL_Mute` — A/B внутри одного звонка

### 11.1 Что проверяли

Гипотеза: микрофон телефона можно вывести из сотового аплинка вендорским
параметром HAL `Set_SpeechCall_UL_Mute=1`, не трогая голосовой путь.
Риск был в том, что параметр глушит весь аплинк вместе с инъекцией агента.

Чтобы проверить это одним звонком, а не пересборкой на каждый вариант, в

|---|---|

Файлы читаются через root-shell на каждом цикле статистики, поэтому рычаг

### 11.2 Замер (звонок 00:12:39, устройство в режиме ожидания)

| время | событие | `capRMS` |
|---|---|---|
| 00:12:48 | `Set_SpeechCall_UL_Mute=1` применён | **13** (до) |
| 00:12:53 | через 5 с после мута | **1** — тишина |
| 00:12:58 | `Set_SpeechCall_UL_Mute=0` применён | **1** (до) |

Абонент в это время говорил непрерывно.

**Вывод: параметр глушит не только микрофон, но и отвод модемного downlink'а

правильный класс рычагов: оно меняет, что *модем* слышит, и не трогает
отвод модема в захват.

## 12. Открытая задача: микрофон вне сотового звонка

### 12.1 Требование

Микрофон телефона не должен попадать в сотовой аплинк (абонент не должен
слышать комнату), **при этом**:

* агент обязан слышать абонента → нельзя глушить модемный downlink;
* абонент обязан слышать агента → нельзя глушить модемный аплинк, в который
  вводится инъекция (`incall_music_uplink → Telephony Tx`).

Значит глушить можно только **до** смешивания микрофона с инъекцией, то есть
на уровне источника микрофона или его усиления.

### 12.2 Что уже исключено (замерено)

| рычаг | результат |
|---|---|
| `Speech_UL_Mute`, `Speech_Mic_Mute` (микшер) | пишутся и читаются как `On`, но микрофон остаётся в звонке (18:03) |
| `isMicrophoneMute` / `Telecom.setMuted` | снимают весь голосовой путь (17:08) |
| `Set_SpeechCall_DL_Mute`, `Speech_DL_Mute`, мут `STREAM_VOICE_CALL` | уносят DL модема из захвата агента (17:50) |
| `Set_SpeechCall_UL_Mute` | уносит DL модема из захвата агента (19:12, §11.2) |
| PCM `VOW_Capture` | принадлежит HAL, открытие ломает голосовой путь (17:50) |

### 12.3 Кандидаты (не проверены — тест отложен на завтра)

## 13. Направление SIP → GSM: «звук из лишнего звена»

По dialplan (`/etc/asterisk/extensions_custom.conf`):

```
[gsm-outbound]
exten => _+X.,1,NoOp(GSM gateway: outbound to ${EXTEN})
 same => n,Dial(PJSIP/${EXTEN}@1001,60)
```

То есть в исходящем направлении PBX просит **шлюз** поставить сотовый звонок
на указанный номер. Если агент звонит на номер SIM самого шлюза
(`380939104994`), шлюз звонит сам себе: сотовый вызов приходит на тот же
телефон, и вторая нога слышит первую. Это и есть «звук из лишнего звена» —
не дефект моста, а самозвонок теста.

Правильный тест исходящего направления: агент звонит на **другой**
сотовый номер (например, на второй мобильный), а не на номер шлюза.

## 15. Итерация 7 (24.11.2026, 18:03–18:07): направление SIP → GSM

### 15.1 Что показал звонок

Звонок в исходящем направлении: агент с расширения 40181 звонит на мобильный,
шлюз ставит сотовый вызов (`Making GSM call to +380507127621`), мост на PBX
(`PJSIP/1001 ↔ PJSIP/40181`) стоит 18:03:51–18:07:49 — сигналинг в этом
направлении в порядке.

Свип рычагов шёл внутри звонка:

| время | рычаг | `capRMS` после |
|---|---|---|
| 18:04:38 | `MTKAIF_ADDA6_ONLY=1` | 1044 → **20** |
| 18:05:08 | `UL_SRC_MUX=DMIC` | 21 → **1** |
| 18:05:39 | `VOW_UL_SRC_MUX=DMIC` | 1 |
| 18:06:09 | `Set_BGS_UL_Mute=1` | 1 (всплеск 566) |

**`UL_SRC_MUX=DMIC` действительно убирает микрофон телефона из сотового
аплинка** — пользователь подтвердил: «во второй половине звонка микрофон
кубота уже не участвовал». **Но тем же ходом умирает отвод модемного
downlink'а** (`capRMS=1`, «Dead air 6s»): агент перестаёт слышать абонента.

Итог тот же, что и у вендорского `Set_SpeechCall_UL_Mute` (§11.2): на MT6855
**любой** рычаг, который убирает микрофон из аплинка, уносит и downlink модема.
Торг двух сторон неприемлем — оба раза приоритет у голоса абонента.

### 15.2 Настоящая причина «звука из лишнего звена» — не микрофон

Пользователь описал симптом так: «слышно микрофон кубота… но при этом с
динамика кубота было слышно человека который говорил в телефон». То есть
**телефон играл голос дальней стороны в комнату**, и микрофон телефона это
подхватывал — отсюда и «лишний звонок» на стороне абонента: он слышал
повтор собственной реплики, пришедший через динамик телефона.

Путь голоса дальней стороны подтверждён `dumpsys audio`:

```
usage=USAGE_VOICE_COMMUNICATION  stream: STREAM_VOICE_CALL  → type:earpiece
```

То есть модемный downlink играется в ухо (`STREAM_VOICE_CALL` → earpiece),
а наш трек инъекции идёт в устройство `TYPE_TELEPHONY` (`device=18/X100`) —
в модем, не в динамик.

При этом мут выхода был записан и переподтверждался каждый тик:

```
18:03:53 Handset output muted: RCV Mux: Open / LOL Mux: Open (capRMS before=2164)
18:04:38 Handset output still muted: RCV Mux: Open
... и так до конца звонка
```

**Но это было самообманом**: `tinymix 'RCV Mux' Open` печатает значение, которое
*только что записал*, а не то, которое осталось в контроле. HAL переписывает
`RCV Mux` / `LOL Mux` при программировании голосового пути (это делают пути
`turnon` в `/vendor/etc/audio_device.xml`: `RCV Mux=Voice Playback`,
`LOL Mux=Playback`), и мы этого не видели.

### 15.3 Что исправлено в приложении

Добавлена read-back проверка выходного пути (`DeviceProfile.mixerHandsetOutputMuteVerifyCmd`):
раз в тик приложение **читает** `RCV Mux`, `LOL Mux`, `DAC In Mux` и
`Handset Volume` и пишет в лог:

* если оба мукса `Open` — `Handset output path: RCV Mux: Open | LOL Mux: Open | …`;
* если HAL вернул путь — предупреждение
  `Handset output path OPEN — the HAL undid the mute: …`.

Это превращает слепое пятно в измерение: следующий звонок покажет, кто
переписывает мукс и как часто.

## 16. Итерация 8 (27.11.2026): полный diff микшера и настоящая причина утечки

### 16.1 Как искали

Замер «мут выхода не работает» упирался в одно слепое пятно: команда
`tinymix 'RCV Mux' Open` печатает значение, которое *только что записала*,
а не то, которое осталось в контроле. Read-back, добавленный в приложение
(§15.3), показал: `RCV Mux` и `LOL Mux` **держатся** `Open` весь звонок —
HAL их не перезаписывает. Значит утечка идёт другим путём.

Дальше сработал другой приём: **полный diff всех 435 контролов микшера,
«покой» против «звонок»**. Снимок снимается до звонка и восемь раз во
время; разница показывает, что именно HAL включает на время разговора.

### 16.2 Что HAL открывает на время звонка

Выход (голос модема → комната):

```
PCM_2_CAP → HW_SRC_3 → I2S3 → усилитель aw_dev_0 (профиль Receiver)
```
включается через `I2S3_CH1/CH2 HW_SRC_3_OUT_CH1/CH2 = On`.

Вход (микрофон → аплинк модема):

```
ADC_L (Left Preamplifier) → PGA_L (AIN0) → HW_SRC_1 → PCM_2_PB → UL1_CH1 → MISO1 → модем
```
включается через `HW_SRC_1_IN_CH1/CH2 ADDA_UL_CH1/CH2 = On`, `MISO1_MUX = UL1_CH1`.

Плюс `STF_CH1/CH2 ADDA_UL_CH* = On` — **сидтон**, микрофон телефона,
проигрываемый локально.

`RCV Mux` / `LOL Mux` — это аналоговые выходы кодека, они к голосу модема
отношения не имеют. Голос дальней стороны идёт в комнату по I2S.

### 16.3 Что сделано в приложении

`mixerHandsetOutputMuteCmd` теперь глушит три вещи (поздно, +3 с, и
переподтверждается каждый тик):

| рычаг | что это |
|---|---|
| `RCV Mux` / `LOL Mux` = `Open` | аналоговые выходы кодека |
| `I2S3_CH1/CH2 HW_SRC_3_OUT_CH1/CH2` = `Off` | **голос модема → усилитель** |
| `STF_CH1/CH2 ADDA_UL_CH1/CH2` = `Off` | **сидтон (микрофон в комнате)** |

Восстановление в конце звонка возвращает эти переключатели в состояние покоя
(`Off`) — HAL ставит их сам на каждом звонке.

### 16.4 Замер после правки (контрольный звонок 11:50)

| сторона | было | стало |
|---|---|---|
| Cubot (шлюз) | голос абонента слышно в комнате | **молчит** |
| айфон (абонент) | слышно эхо собственного голоса | **чисто** |
| агент (SIP) | слышит абонента | **слышит абонента** |

То есть «звук из лишнего звона» был не чем-то отдельным, а **эхом, которое
возникало само**: голос дальней стороны играл в комнату с телефона, микрофон
подхватывал его обратно, и абонент слышал себя. Разрыв I2S-пути убирает и
причину, и следствие.

### 16.5 Что осталось: комната в захвате агента

Агент слышит **и** голос абонента, **и** голос комнаты возле Cubot'а. То есть
микрофон телефона попадает не в сотовой аплинк (айфон чист), а в **захват**,
который приложение шлёт на PBX.

Испробованные способы убрать микрофон из захвата — все убирают голос абонента
вместе с ним, потому что AIF-нода `HW_SRC_1` полнодуплексна: по ней идёт и
микрофон в модем, и downlink модема в AP:

| рычаг | микрофон из захвата | голос абонента в захвате |
|---|---|---|
| `Set_SpeechCall_UL_Mute=1` | уходит | **уходит** (`capRMS` 13 → 1) |
| `UL_SRC_MUX=DMIC` | уходит | **уходит** (`capRMS` 21 → 1) |
| `HW_SRC_1_IN_CH1 ADDA_UL_CH1=0` | остаётся | **уходит** (`capRMS` → 1) |
| `Set_SpeechRec_DL_Pos=0..3` | не меняется | не меняется |

Последний — единственный, кто не ломает голос абонента, но и комнату не
убирает: параметр меняет положение отвода DL в записи, а состав записи не
трогает.

**Кандидат на следующий шаг**: цифровой шлюз — приложение умеет считать
уровень и применить шумовой гейт. Комната в захвате sits на уровне 12–25 RMS,
голос абонента — 800–3000 RMS, так что гейт в районе 150–300 отрежет комнату,
не тронув голос. Цена: в паузах абонента агент будет слышать тишину.

## 18. Микрофон выведен из разговора (27.11.2026, 13:10–13:29)

решение, и его пришлось отменить: гейт **маскирует** симптом, а не устраняет
его. При пороге 120:

* микрофон по-прежнему в разговоре — любой резкий звук в комнате уходит агенту;
* тихая речь абонента срезается (порог стоит выше её уровня);
* в логе это выглядит как «шум убран», хотя убран только шум.

Задача была поставлена правильно: **убрать микрофон из разговора**, а не
приглушить комнату.

### 18.1 Почему прежние рычаги не работали

Полный diff микшера «покой vs звонок» (435 контролов, 27.11 11:21) дал карту
пути на MT6855:

```
микрофон:  ADC_L → PGA_L(AIN0) → ADDA_UL → HW_SRC_1 → PCM_2_PB → UL1 → MISO1 → модем
голос модема (DL): цифровой; в CPU приходит отдельной нодой PCM_2_CAP
динамик:   PCM_2_CAP → HW_SRC_3 → I2S3 → усилитель aw_dev_0 (Receiver)
```

Ключ: **DL модема — цифровой, а микрофон — аналоговый**. Все прежние рычаги
рубили *маршрут* (`UL_SRC_MUX`, `HW_SRC_1_IN*`, `Set_SpeechCall_UL_Mute`), а
маршрут у микрофона и у downlink общий — `HW_SRC_1` полнодуплексна. Отсюда
«уезжает DL вместе с микрофоном».

Разрыв надо делать там, где эти две ветки ещё не смешаны, — на аналоговом
входе микрофона.

### 18.2 Рычаг

`PGA_L_Mux` — переключатель аналогового входа левого PGA (предусиления), в
который приходит встроенный микрофон AIN0:

| значение | состояние |
|---|---|
| `AIN0` | микрофон подключён (HAL ставит это при программировании пути звонка) |
| `None` | микрофон отключён |

Значение `None` — не «приглушение», а именно **отсутствие подключения**:
сигнал микрофона не доходит ни до одного узла, а цифровой downlink модема
идёт мимо этой ветки.

### 18.3 Замер в живом звонке (13:08–13:11, рычаг вручную)

| момент | микрофон | фон захвата | голос абонента |

| 13:08:46–13:10:05 | подключён (`AIN0`) | 12–28 RMS | 2297–3043 RMS |

с отключённым — **только голос абонента**.

Первая попытка автоматизации провалилась: резка была добавлена в профиль

Резка добавлена **в оба** цифровых профиля, и тест проверяет оба.

Механизм в `RtpSession`:

* `applyHandsetMicCut()` — при старте захвата (первый кадр, комната ещё не

* восстановление в конце звонка возвращает микрофон (`AIN0`) — телефон
  остаётся обычным.

списка, read-back покажет «всё заглушено» — а звук продолжится. Тогда нужна
замерка: полный diff микшера «покой vs звонок» (как в §18.1) на этом

## 20. Автоответ и ранняя медиа (28.11.2026)

Задача: то, что оператор говорит **до поднятия трубки**, должно доходить
до агента.

### 20.1 Почему оно терялось

Сотовый оператор объявляет своё до того, как второй абонент ответил:
«этот номер недоступен», «соединяем с оператором», платёжный запрос.
Этот звук существует только в нисходящем канале сотовой стороны, и
канал открывается **только когда нога отвечена**.

Схема была такая:

```
агент → PBX → INVITE → шлюз набирает GSM
                          │
                          └─ ждём, пока GSM позвонит в ACTIVE
                                └─ 200 OK агенту, RTP, разговор
```

До `ACTIVE` сотовой ноги шлюз не отвечал, поэтому объявление оператора
игралось в никуда: ни в RTP не попадало, ни агент его не слышал. Ровно
тот случай, который на GoIP закрывается автоответом или ранней медиа.

### 20.2 Что сделано

**Автоответ сотовой ноги.** Шлюз отвечает на сотовый вызов сам, не дожидаясь
дальней стороны. Нисходящий канал открывается, объявление попадает в
захват `VOICE_CALL`, и RTP-сессия уносит его агенту.

**Ранняя медиа в обе стороны.**

* Шлюз как вызывающий (GSM → SIP): сервер присылает `183 Session Progress`
  с SDP — значит медиапоток уже живой. Шлюз запоминает адрес и, если
  сотовая нога уже поднята, стартует RTP немедленно: агент слышит
  сотовую сторону, пока его телефон ещё звонит.
* Шлюз как вызываемый (SIP → GSM): при подъёме сотовой ноги шлюз отвечает
  `183 Session Progress` со своим SDP, стартует RTP и только потом
  подтверждает звонок `200 OK`. Тег `To` у обоих ответов один — это один
  диалог.

**Что это меняет в протоколе.** `183` несут SDP, поэтому разбор SDP переехал
из ветки `200 OK` в общий разбор предварительных ответов (`180`/`183`).
Кодек, выбранный в ранней медиа, не затирается ответом без SDP: медиапоток
уже идёт с ним.

### 20.3 Настройки

| ключ | по умолчанию | смысл |
|---|---|---|
| `auto_answer_out` | вкл | автоответ сотовой ноги, которую шлюз набирает сам |
| `auto_answer_in` | выкл | автоответ входящего сотового вызова |
| `auto_answer_delay_ms` | 1200 | задержка до автоответа, 0…15000 |
| `early_media` | вкл | `183` с SDP в обе стороны |

Входящий автоответ по умолчанию **выключен**: абонент слышал бы тишину
вместо звонка, пока телефон агента ещё звонит, — это читается как
«answered, но никто не говорит».

Задержка — узкое окно: слишком рано — сеть ещё не подняла канал, слишком
поздно — начало объявления потеряно. Для своего оператора подбирается
подбором.

### 20.4 Чего ждать в логе

```
GSM: answering the cellular leg now
Answering the cellular leg now (auto-answer) — the operator's announcement becomes audible
Early media offered to the server (183 + SDP), port=31000
GSM call active
RTP: ... capRMS=... (идёт объявление оператора)
```

Если в логе есть `Auto-answer: the cellular leg is already active` — значит
дальняя сторона ответила сама, и автоответ не понадобился.

### 20.5 Ограничения

* Автоответ исходящей ноги — это ответ на вызов, который шлюз **сам**
  набрал. Сотовый оператор после этого считает звонок отвеченным; если
  дальняя сторона не поднимет трубку, соединение живёт до его таймаута.
* `Call.answer()` на исходящем вызоне — не штатная операция для Telecom.
  На IMS/VoLTE это штатный «accept early media», на CS — может быть
  отклонено. Отказ ловится и пишется в лог
  (`GSM answer failed: …`), мост при этом не падает.
* Ранняя медиа со стороны сервера приходит не всегда: `183` с SDP шлёт
  только тот сервер, у которого на той стороне есть ранняя медиа.

### 20.6 Побочный эффект автоответа: источник захвата

Обнаруженный при разборе механизма, а не в логе: детектор тишины в
`RtpSession` списывает источник захвата, который не доказал дееспособность
(`sourceProven == false`), после лимита тишины — и переходит к следующему
источнику в списке. А следующий в списке — это микрофон.

Раньше это было почти безопасно: сотовую ногу отвечали только тогда, когда
агент уже поднял трубку, и абонент к тому моменту обычно уже говорил.
С автоответом нога поднимается раньше, чем сеть начнёт говорить, и первые
секунды захвата — законная тишина. Список источников на этом телефоне
выглядит так: `VOICE_CALL` → `VOICE_DOWNLINK` → `VOICE_RECOGNITION` →
`MIC`. Если `VOICE_CALL` списывается в первые секунды, дальше может
подставиться микрофон — а это комната вместо звонка.

Поэтому у сессии появился признак `allowSilentStart`: его выставляет
оркестратор, когда ногу отвечали мы, а не дальняя сторона. С таким
признаком непроверенный источник не списывается в первые 10 секунд
молчания (`SILENT_START_GRACE_MS`). Для обычных звонков поведение не
меняется — там грань по-прежнему работает как раньше.

В логе это видно так:

```
Source VOICE_CALL silent early in an early-answered call — keeping it for now
```

### 20.7 183 вместо 180 с самого начала

Наблюдение с сервера (13:12:13, звонок на +74959999991): PBX отправил INVITE,
шлюз ответил **180 Ringing** — и больше ничего. Ни 183, ни 200 OK за 21 секунду,
пока не сработал таймаут Dial. CDR: `NO ANSWER`.

183 в коде отправлялся только после того, как сотовая нога доходила до
ACTIVE. То есть при недоступной дальней стороне агент видел «звонок идёт» и
тишину.

Что поменялось:

* **183 с SDP отправляется сразу**, как только пришёл INVITE. Сервер на
  этом поднимает early-media мост к агенту: агент слышит сотовую сторону
  **пока его телефон ещё звонит**. Это и есть модель GoIP.
* **RTP-сессия поднимается, когда сотовая нога поднялась**, — не раньше.
  Раньше было желание поднять её вместе с 183, чтобы захват был готов к
  моменту, когда сеть заговорит. Но HAL переписывает голосовой путь, когда
  программирует звонок, и настройка инъекции incall_music, записанная до
  этого, пропадает вместе с ней — голос агента не дошёл бы до абонента
  вообще. Переключать `incall_music_enabled` повторно нельзя: на SM6150
  второй переход ронял захват (`rawRMS` 208 → 0). Поэтому порт, названный в
  183, просто тот же, на котором поднимется сессия: ранняя медиа и ответ —
  один поток, один порт, один диалог.
* **200 OK** уходит, когда сотовая нога поднялась. До этого агент слышит
  сотовую сторону через early-media мост, который сервер поднял по 183.

### 20.8 Ответ модему надо давать повторно

`Call.answer()` уходит в модем, а модем берёт его не сразу: канал должен
быть поднят сетью. Повтор ответа был привязан к состоянию `RINGING` — а у
исходящего вызова, который набрал сам шлюз, такого состояния **не бывает**
вовсе: DIALING → CONNECTING → ACTIVE.

Итог: у раннего ответа был ровно один шанс, и он приходился на момент, когда
сеть ещё не подняла канал. Теперь повтор идёт по всем состояниям до
ACTIVE (`GsmCallStates.isUpYet`), а для раннего ответа он принудительно
включён: 250 мс × 20 попыток = 5 секунд на то, чтобы модем принял ответ.

### 20.9 Что ждать в логе новой сборки

```
Early media offered to the server (183 + SDP), port=31234
Auto-answer of the cellular leg in 1200ms — catching the operator's announcement
GSM: answering the cellular leg now
GSM call not up yet (state=2) — answering again (1/20)
GSM call active
```

На сервере при этом видно:

```
PJSIP/1001-000000xx is ringing              <- 183 с SDP
PJSIP/1001-000000xx is making progress       <- сервер принял раннюю медию
PJSIP/1001-000000xx answered PJSIP/40181-…   <- 200 OK, агент соединён
```

Если `is making progress` нет — 183 до сервера не дошёл или в нём не было
SDP. Если `is making progress` есть, а `answered` нет — сотовая нога не
поднялась, и смотреть надо в лог телефона.

## 21 Объявление оператора в SIP (v1.4.23)

### 21.1 Замер, который всё прояснил

Тест 28.11 13:39, v1.4.22 (релиз опубликован в 13:28 EET):

```
13:39:49  app_dial.c: PJSIP/1001-000000de is making progress passing it to PJSIP/40181-000000dd
13:39:58  macro-dialout-trunk exited non-zero → CDR: duration=8, billsec=0, disposition=NO ANSWER
```

Сервер принял **183 с SDP** (значит, объявление оператора он услышал), но
**200 OK не пришёл**: сетовая нога так и не дошла до `STATE_ACTIVE`, RTP-сессия
не поднялась, поэтому в SIP была тишина, а объявление играло на самом Cubot —
сеть отдаёт его на нисходящий канал (downlink), пока нога в состоянии
`CONNECTING` (дальний абонент « alerting»).

Ранний ответ модему (`Call.answer()` на исходящем вызове) на этом устройстве
не срабатывает: нога остаётся в `CONNECTING`. Значит, объявление можно поймать
только одним способом — **читать downlink в тот момент, когда нога ещё не
поднята**.

### 21.2 Что изменилось

* **RTP-сессия поднимается вместе с 183**, а не на `STATE_ACTIVE`. Порт из
  183 — тот же, на котором работает сессия: ранняя медиа и ответ остаются
  одним потоком. Сервер принимает 183, поднимает early-media мост и пересылает
  то, что шлёт шлюз, агенту.
* **Ранняя фаза** (`RtpSession(earlyCapture = true)`):
  * список источников короткий — `VOICE_CALL`, затем `VOICE_DOWNLINK` (если
    профиль говорит, что он читается), и последним микрофон: комната не
    должна попадать к агенту вместо абонента, но микрофон — единственный
    источник, который снимет объявление, пока телефон играет его в колонку;
  * молчащий источник списывается через 1,5 с, а не через 6 (иначе половина
    объявления проходит мимо);
  * инъекция и глушения **не пишутся** — HAL переписывает голосовой путь, когда
    программирует вызов, и всё написанное до этого теряется.
* **Когда нога поднялась** (`applyForActiveLeg()`): захват открывается заново
  (источник, созданный до программирования вызова, может остаться привязан к
  пути, который молчит навсегда), пишется инъекция, заново указывается
  устройство вывода (`telephony TX` появляется только при активном вызове),
  глушится колонка и отрезается микрофон.
* **Ранний ответ исходящей ноги выключен по умолчанию** — он не работает
  (21.1), а объявление теперь ловится ранним захватом.
* Таймаут RTP не считается, пока нога не поднята: в ранней фазе поток
  односторонний (серверу нечего отправлять, пока телефон агента звонит), и
  таймаут снёс бы живой вызов.

### 21.3 Что ждать в логе новой сборки

В лог приложения (Settings → Logs → Copy) теперь попадают состояния сотовой
ноги и статистика потока:

```
AUDIO: GSM state: DIALING
AUDIO: GSM state: CONNECTING (the far end is alerting)
RTP: Early media: capturing the cellular downlink at … while the leg alerts
RTP: Capture: source=VOICE_CALL rate=8000 …
RTP: RTP: capRMS=… rawCapRMS=… src=VOICE_CALL …
RTP: Capture reopened after the cellular leg came up
AUDIO: GSM state: ACTIVE
```

Ключевая строка — `rawCapRMS` в ранней фазе: если он не нулевой, downlink
объявления действительно снят и агент его слышит. Если он нулевой, значит
цифровой источник в состоянии `CONNECTING` молчит, и спасение — акустический
источник (микрофон), который подхватывает объявление с колонки.

### 21.4 Чего ждать на сервере

```
app_dial.c: PJSIP/1001-… is making progress passing it to PJSIP/40181-…
```

и, если нога поднялась:

```
app_dial.c: PJSIP/1001-… answered PJSIP/40181-…
```

### 21.5 Динамик шлюза замолчал (v1.4.24)

Замер 28.11 (v1.4.23): объявление **дошло до агента** — ранний захват сработал,
но оно же продолжало играть из динамика самого шлюза. Шлюз — не абонент:
звук должен уходить агенту, а колонка на телефоне молчит.

Глушение выхода в ранней фазе было намеренно отложено: пока нога не
поднялась, телефон играет объявление в колонку, а микрофон — последний
источник, который может снять его. Заглушить колонку раньше — значит
выбросить объявление совсем, если захват не сработает.

Поэтому глушение теперь пишется **после того, как захват доказал, что несёт
звук** (`rawCapRMS > 0` → источник признан рабочим):

* в тот момент — один раз — закрывается выход телефона
  (`RCV Mux` / `LOL Mux` = Open, `I2S3_CH*` Off, `STF_CH*` Off);
* keeper (каждые 4 с) продолжает удерживать его закрытым и в ранней фазе:
  HAL переписывает эти контролы, когда программирует вызов;
* при подъёме ноги глушение пишется в любом случае (как и раньше).

То есть объявление не может исчезнуть ни в одном варианте: пока его несёт
захват — оно идёт агенту, а колонка замолкает; если захват молчит — колонка
продолжает играть, и в логе это видно по `rawCapRMS=0`.

В логе:

```
RTP: The capture carries the announcement — the handset's loudspeaker is closed
RTP: Handset output muted (capRMS before=…): …
```

### 22.2 Что нужно на сервере

`/etc/asterisk/extensions_custom.conf`, контекст `[from-gsm-gateway-did]` —
сейчас там одна запись (старый номер `380939104994`), остальное уходит в

```
exten => 79177454214,1,NoOp(GSM DID ${GSM_DID} -> 40181)

 same => n,Hangup()
```

Ключ — номер SIM-карты шлюза **без «+»**: контекст снимает «+» через
`${EXTEN:1}`, а RURI шлюза — это его собственный MSISDN (`inboundSipDestination`
в приложении берёт именно его). Перезагрузка: `asterisk -rx 'dialplan reload'`.

Для схемы на 100 телефонов таких записей по одной на каждую линию.

### 22.3 SMS: 401 — это не пароль

```
NOTICE res_pjsip/pjsip_distributor.c: Request 'MESSAGE' from
  '<sip:MTC.Dengi@185.82.73.76>' failed for '153.75.85.65:5062' - Failed to authenticate
```

Request-URI указывает на **имя, а не на SIP-аккаунт**: оператор отдаёт номер
абонента как «MTC.Dengi», и это значение (`sms.to`) уходит прямо в RURI.
Эндпойнта с таким пользователем на сервере нет, и запрос не проходит
аутентификацию — в отличие от вызова, который уходит с `From: <sip:1001@…>`
и матчится по нему.

Как надо: адресовать MESSAGE своему аккаунту (`sip:1001@server`), а номер
абонента класть в `P-Asserted-Identity` и `X-SMS-To` — ровно как в вызовах.
Вторая половина — на сервере: обработчика MESSAGE в диалплане нет вообще
(`grep -ri message /etc/asterisk/extensions*.conf` — пусто), так что принятое
сообщение сейчас некуда деть.

## 23 Входящий звонок: назначение задаёт шлюз (v1.4.25)

### 23.1 Почему номер SIM — плохой ключ маршрутизации

Замер 28.11 (см. §22): шлюз отправил INVITE, сервер его аутентифицировал и
повесил — `GSM DID +79177454214 not mapped`. Ключом маршрутизации был номер
SIM-карты шлюза, то есть **телефонный номер самого шлюза**. Это плохой ключ:

* на сервере нужна запись в диалплане на каждую линию, и их надо держать в
  соответствие с SIM-картами;
* номер SIM меняется при замене карты, и маршрут едет вместе с ним;
* в CDR виден номер SIM шлюза, а не номер, на который звонок поставлен.

### 23.2 Что теперь делает шлюз

В настройках появилось поле **«Inbound SIP destination»** — SIP-номер, на
который уходит входящий звонок (например `40181` — это то, что в GoIP
называется «куда звонить»).

* Поле пустое → работает как раньше: Request-URI = номер SIM-карты
  (обратная совместимость со старыми серверными правилами).
* Поле заполнено → Request-URI = это число, и сервер звонит именно туда.
  Шлюз по-прежнему представляется своим аккаунтом (`From: <sip:1001@…>`),
  а номер GSM-абонента идёт в `P-Asserted-Identity` — так же, как в вызовах.
* Значение проверяется: только цифры с необязательным «+». Негодное значение
  (и значение, равное собственному аккаунту шлюза — иначе вызов вернулся бы
  в шлюз) отбрасываются с записью в лог, маршрут остаётся прежним.

Логика — `bridge/InboundDestination.kt`, тесты — `InboundDestinationTest`.

### 23.3 Что нужно на сервере (одно правило на все линии)

Вместо записи на каждый DID — одно правило, которое звонит туда, куда шлюз
сказал:

```
[from-gsm-gateway]
exten => _X.,1,NoOp(GSM gateway: inbound -> ${EXTEN} from ${CALLERID(num)})
 same => n,Dial(PJSIP/${EXTEN},60)
 same => n,Hangup()
```

Старое правило с таблицей DID (`_+X.` → `from-gsm-gateway-did`) можно оставить
для шлюзов, у которых поле назначения ещё пустое: `_+X.` — более специфичный
шаблон, поэтому он сработает первым.

В CDR теперь видно, куда звонок поставлен: `dst` = назначение (40181),
`src` = номер GSM-абонента.

### 23.4 Как проверить

В приложении: Settings → Inbound SIP destination → `40181` → Save. Телефон
звонит на номер шлюза — у агента (40181) звонит SIP-телефон, шлюз берёт
сотовую трубку, мост работает.

```
~/.ssh/fpbx-run.sh "grep -h 'inbound ->' /var/log/asterisk/full | tail -5"
~/.ssh/fpbx-run.sh 'mysql -B asteriskcdrdb -e "SELECT calldate,src,dst,duration,billsec,disposition FROM cdr ORDER BY calldate DESC LIMIT 5;"'
```

## 24 USSD-запросы из приложения (v1.4.26)

### 24.1 Зачем

Телефон-шлюз отказывается нормально работать, пока приложение не выбрано
по умолчанию для звонков: оператор отдаёт USSD-ответы в приложение, которое
владеет ролью dialer, и без неё коды не проходят.

Раньше USSD отправлялся только одним способом — из SIP: если в номере
исходящего вызова стоял MMI-код (`*100#`), шлюз не ставил звонок, а
отправлял код в сеть (`GsmCallManager.sendMmi` → `CallOrchestrator`).
Из самого приложения отправить код было нельзя.

### 24.2 Что стало

На главном экране — карточка **USSD REQUEST**:

* поле для кода (`*100#`), кнопка **Send request**;
* выбор SIM: «Default SIM — the one calls go out from» и карты, которые
  видны в системе (`SIM 1 · оператор · IMEI`);
* поле ответа: приходит текст, который вернул оператор, либо причина, по
  которой ответа не будет.

Карточка на главном экране, а не в настройках: код спрашивают часто
(баланс, минуты), и до него должен быть один тап.

Путь запроса: UI → `GatewayService.requestUssd()` (действие
`ACTION_USSD_SEND`) → `GsmCallManager.sendUssd()` →
`TelephonyManager.sendUssdRequest()` → ответ приходит в
`UssdResponseCallback` на главном лупере → сервис пишет строку в лог и
отдаёт результат в UI широковещанием `USSD_RESULT_ACTION`.

Запрос идёт через модем и **не зависит от SIP**: шлюз может быть не
зарегистрирован, а код всё равно уйдёт оператору.

### 24.3 Правила для кода

Логика — `ussd/UssdRequest.kt`, тесты — `UssdRequestTest` (25 тестов
всего по USSD).

* Код начинается с `*` или `#`. Без этого запрос неотличим от номера, а
  номер — это звонок.
* Только цифры, `*` и `#`; пробелы выбрасываются (`* 100 #` → `*100#`).
* Нужен хотя бы один цифровой символ.
* Длина — до 182 символов (3GPP TS 27.007).
* Если закрывающего `#` нет, он добавляется: сессия USSD закрывается
  хешем, и без него сеть держит сессию открытой и не отвечает вовсе.

### 24.4 Ограничения платформы (важно знать)

* `sendUssdRequest()` — с Android 8 (API 26). Ниже код ставится как
  звонок (старая манера), ответ приходит на сам телефон. На шлюзе Android
  15, так что этот путь — только для совместимости.
* Платформа требует `CALL_PHONE` — приложение его запрашивает при первом
  запуске. Приложение стоит priv-app и имеет `MODIFY_PHONE_STATE`.
* Выбор конкретной SIM работает с Android 12 (API 31): `createForSubscriptionId`
  became instance-методом, а статический вариант убран из SDK, под который
  собирается приложение. Ниже Android 12 код уходит с SIM по умолчанию.
* Android 17 (QPR2) ограничил **переадресацию** (`*21*…#`) для приложений,
  у которых есть только `CALL_PHONE`: такой запрос возвращается с
  `USSD_ERROR_NOT_ALLOWED`. Шлюз — системное приложение (priv-app), поэтому
  освобождён от этого ограничения. На Android 15 (шлюз) этого ограничения
  нет вовсе.

### 24.5 Как проверить

1. Обновить модуль на телефоне (Magisk → Modules → Install → zip → Reboot).
2. Открыть приложение, дать разрешения, выбрать SIM.
3. В карточке USSD ввести `*100#` (баланс оператора) → Send request.
4. Ответ появляется в поле ответа и в логе приложения.

В логе:

```
USSD *100# → Your balance is 123.45 RUB
```

## 25 Обновление приложения из самого приложения (v1.4.27)

### 25.1 Зачем

Шлюз работает без присмотра: некому открыть приложение, скачать новую
сборку и поставить её. Значит, обновление должно происходить внутри шлюза:
проверить, есть ли новее, и поставить самому.

### 25.2 Как это работает

Лента релизов — публичная: `https://api.github.com/repos/GenaLC/android-tools/releases/latest`.
Ответ — небольшой JSON, в котором есть тег версии и список файлов релиза.

```
UpdateChecker.fetch()      → релиз: тег, ссылка на APK, размер, заметки
AppVersion.isNewer()       → «1.4.27» новее «1.4.26»?
ApkInstaller.install()     → скачать, проверить, поставить
```

Порядок действий:

1. **Проверка.** Тег из ленты сравнивается с версией приложения по
   разрядам: `1.5` новее `1.4.26`, `1.4` старее `1.4.1`. Префикс `v` и суффикс
   (`-beta`) в сравнении не участвуют.
2. **Скачивание.** APK из релиза — 5 МБ — кладётся в кэш приложения.
3. **Проверка подписи.** Скачанный файл обязан быть тем же приложением
   (`com.callagent.gateway`) и подписан тем же ключом, что и работающее.
   Это и есть проверка подлинности: чужая подпись — отказ, файл не ставится.
4. **Установка.** Через root: `cp` в `/data/local/tmp` и
   `pm install -r`. Приложение — системное (priv-app), поэтому обновление
   ложится рядом с копией модуля, и **привилегии сохраняются**: Android
   выдаёт обновлённому системному приложению те привилегированные права,
   которые есть у его системной копии (проверено по AOSP:
   `PermissionManagerService.checkPrivilegedPermissionAllowlist` — для
   updated system app allowlist не проверяется). Мост и права модема
   продолжают работать.
5. **Без root** — системный установщик: файл отдаётся ему через FileProvider,
   дальше подтверждает человек. Этот путь требует права «установка
   неизвестных приложений» для Device Tools.

### 25.3 Когда обновление происходит

* **Само, при старте шлюза** — сразу после того, как SIP-клиент поднялся.
  Проверка идёт отдельным потоком: сеть не ждёт ленту, лента не задерживает
  регистрацию. Переключатель в настройках («Install a newer build on its
  own») это поведение включает и выключает; по умолчанию включено.
* **Вручную** — кнопка «Check for updates» в настройках.

Во время разговора обновление **не ставится**: сборка, положенная поверх
работающей, останавливает процесс, а вместе с ним — разговор. Связь
ценнее сборки: обновление ждёт свободной линии и встаёт при следующем
старте.

### 25.4 Что происходит после установки

Процесс приложения останавливается, система запускает его заново, а
`BootReceiver` (MY_PACKAGE_REPLACED) поднимает шлюз заново. На следующей
загрузке `service.sh` модуля делает `pm path com.callagent.gateway` и
кладёт активный APK в priv-app оверлей — база модуля приходит в
соответствие с обновлённой версией сама.

### 25.5 Чего обновление не делает

* **Не обновляет сам Magisk-модуль.** Модуль — это zip, его ставит человек
  через Magisk Manager. Привилегированные права выдаются модулем, и если
  сборка захочет новое привилегированное право, его не будет до
  пересборки модуля (так устроена выдача privapp-прав: обновлённое
  системное приложение получает только то, что есть у его системной копии).
* **Не трогает настройки**: сервер, логин, пароль, маршрут входящих и
  прочее переживают обновление — они лежат в настройках приложения.

### 25.6 Как проверить

```
Update: v1.4.27 is newer than 1.4.26
Update: downloading v1.4.27 (5183 KB)
Update: downloaded 5183 KB
Update: v1.4.27 installed over the running build
```

В журнале Magisk после перезагрузки:

```
Synced updated APK from /data/app/~~…/base.apk (reboot needed for priv-app refresh)
```

### 25.7 Проверка самообновления (v1.4.28)

v1.4.28 собрана **только для проверки**: код тот же, что в v1.4.27, —
изменены номер версии и versionCode. Нужна как «триггер»: телефон должен
найти её сам.

Порядок:

1. На Cubot поставить модуль **v1.4.27** (в нём уже есть функция
   обновления) и перезагрузить. Без этого шага телефон не умеет обновляться
   сам и v1.4.28 придётся ставить вручную.
2. Дальше ничего делать не нужно: при старте шлюза приложение спросит ленту
   релизов, найдёт v1.4.28 и поставит её.

Что должно быть видно в журнале приложения:

```
Update: v1.4.28 is newer than 1.4.27
Update: downloading v1.4.28 (5183 KB)
Update: downloaded 5183 KB
Update: v1.4.28 installed over the running build
[v1.4.28] SIP client started, registering with …      ← процесс перезапущен
```

После перезагрузки в журнале Magisk:

```
Synced updated APK from /data/app/~~…/base.apk (reboot needed for priv-app refresh)
```

— это значит, что база priv-app в оверлее модуля приведена в соответствие с
новой версией.

Если в журнале вместо этого:

```
Update: the release feed could not be read (…)        ← нет сети или feed не отвечает
Update: v1.4.28 failed: …                             ← отказ, с причиной в тексте
Update: refused — the build is signed with another key  ← подпись не та
```

— то причина в тексте, а не в телефоне.
